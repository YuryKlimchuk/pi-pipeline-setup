# Сценарий неразрушающей установки

> **Будущая процедура, не исполняемая автоматизация.** Фазы установки ниже не являются этапами workflow разработки. До согласования архитектурных вопросов и создания ресурсов установку нельзя объявлять реализованной.

## Исследование (до записи)

- Прочитать README blueprint, [архитектуру](../docs/architecture.md), [роли](../docs/roles.md), [workflow](../docs/workflow.md) и [модельную конфигурацию](../docs/model-configuration.md).
- Определить точный корень целевого проекта; изучить состояние Git и существующие `.pi/settings.json`, инструкции `SYSTEM.md`/`APPEND_SYSTEM.md`, агентов, skills/prompts/extensions, контекст `AGENTS.md`/`CLAUDE.md` и overrides в проекте/родителях.
- Изучить влияющую пользовательскую конфигурацию Pi **без её изменения и без вывода секретов**. Проверить коллизии имён, пути за пределами проекта/симлинки и ресурсы, которые исполняют код при загрузке.
- Определить стек и необходимость будущего профиля; не предполагать Java/Spring.
- Проверить версии Pi/Node/OpenSpec, выбранную реализацию subagent и параметры доверия. См. [предварительные требования](README.md).
- Получить `openspec context --json`, проверить фактический root/store. Не создавать корень или изменение для проверки. Если корня нет — предложить отдельное явное решение пользователя об `openspec init --tools pi`, не запускать автоматически.

## Подготовка назначений моделей

- Получить фактические provider/ID через `pi --list-models`, учитывая, что запуск Pi может загружать доверенные расширения; не исполнять непроверенный проектный код ради инвентаризации.
- Предложить **Economy / Balanced / Quality**. Пользователь задаёт или подтверждает сопоставление `cheap / medium / expensive` реальным моделям. Стоимость нельзя достоверно классифицировать автоматически.
- Отдельно показать default основной сессии Orchestrator (`defaultProvider/defaultModel`) и итоговую модель **каждой из шести ролей subagent** (`model:`). Включить проектные и ручные overrides с их приоритетом.
- Проверить точные ID, аутентификацию и совместимость насколько возможно. Пробный запрос с возможной стоимостью/отправкой данных — только с отдельного разрешения. Непроверенное так и пометить.
- Отсутствующая модель/зависимость блокирует соответствующую часть плана, не вызывает молчаливый fallback.

## План и обязательное подтверждение

Предъявить пользователю **до записи**:

- перечень «источник → назначение» для каждого нового/изменяемого файла, включая документацию установки в целевом проекте;
- diff/предлагаемые блоки слияния, существующие конфликты и варианты «сохранить / пропустить / согласовать изменение»;
- таблицу назначений моделей, ограничения subagent/QA и состояние зависимостей;
- какие инструкции будут загружаться, какие ссылки требуют переноса/переписывания, что не поддерживается;
- способ резервного копирования и восстановления изменяемых файлов, границы записи и непокрытые риски.

**Дождаться явного подтверждения конкретного плана.** Передача ссылки на blueprint, отсутствие возражений или подтверждение модели не означают разрешения записи всех файлов. Изменившийся план/конфликт требует нового подтверждения. Отсутствие подтверждения в неинтерактивном режиме — остановка.

## Применение согласованного плана (будущая реализация)

- Повторно сверить исходные файлы: если они изменились после плана, остановиться для пересогласования.
- Записывать только перечисленные и подтверждённые файлы, сохраняя пользовательские настройки/неизвестные ключи и инструкции. Не подменять `.pi/SYSTEM.md`, не создавать перекрывающий пользовательские правила `APPEND_SYSTEM.md` молча.
- Для моделей применить предложенный контракт генерации: проектный источник → defaults основной сессии и явный `model:` каждого subagent. Сам YAML ничего в Pi не переключает.
- Не копировать README-конвенции как определения агентов/skills/prompts; не переносить несовместимые пользовательские skills.
- При ошибке остановиться, перечислить фактически выполненные изменения и предложить восстановление; не продолжать с частичной конфигурацией как с успешной.
- Не запускать `openspec init`, глобальную установку зависимостей или изменение настроек доверия как побочный эффект.

## Верификация и отчёт

- Проверить пути, ссылки, сохранность пользовательских файлов, отсутствие изменений вне согласованной области, отсутствие коллизий ресурсов.
- Проверить загрузку ресурсов новым запуском Pi или подходящим `/reload` после пользовательского решения о доверии. Не обещать универсальную команду «список агентов»: обнаружение зависит от выбранного расширения.
- Отдельно проверить модель новой основной сессии и фактические назначения/источники subagents. Resume может восстановить прежнюю модель; текущую основную сессию переключают через `/model`, не через frontmatter.
- Итоговый отчёт: настроено, сохранено, пропущено, неподдерживаемое, не проверено, заблокировано и необходимые ручные действия. Не маскировать отсутствие безопасного запуска тестов как QA readiness.
- В согласованной заранее записи подключения указать commit/version blueprint, версию расширения, источник назначений, процедуру ручного изменения и повторного применения. Формат/путь этой записи ещё предстоит согласовать.

Обновление уже установленного blueprint повторяет тот же цикл исследования, diff и подтверждения. Автоматического live-reload YAML, фоновой перегенерации или молчаливого обновления моделей не предполагается.
