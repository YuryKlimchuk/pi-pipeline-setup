# Proposal

> **Статус:** черновик для Human Gate A. **Gate A не одобрен.** Реализация PoC запрещена до явного одобрения пользователем (этап 5 канонического `docs/workflow.md`).

## Why

P0 (решения D1–D6 утверждены) и P1 (матрица совместимости `docs/compatibility.md` + протокол PoC `docs/poc-protocol.md`) завершены. P2 — изменение `model-configuration-contract` — реализовано (schema, синтетические fixtures, документация; 12/13 задач), но его независимая проверка (задача 5.2: Reviewer + QA) не закрыта, Gate B не достигнут.

Следующая реализационная стадия требует воспроизводимого **проектного установщика** и **шести исполнимых ролей subagent**, чтобы инициализировать новые проекты утверждённым workflow. Первое целевое приложение — Java/Spring-скрапер криптовалют с Telegram-оповещениями (в рамках этого изменения **не реализуется**).

Однако ключевые факты остаются `not-tested` (`docs/compatibility.md`): фактическая модель дочернего процесса, фактический набор инструментов, поведение trust/headless child, файловые побочные эффекты. Выбор реализации subagent не сделан: установлена локальная копия **S3** с неизвестным происхождением/версией, а кандидат **S4** (пример в пакете Pi 1.1.0) не подключён. До подтверждения контракта нельзя писать production-установщик (P6b) или production-роли (P4).

Поэтому нужен **минимальный PoC**, который на disposable-проекте, без изменения глобальной конфигурации Pi, установит восемь свойств из задачи и вернёт санитизированный отчёт с явным перечнем того, что осталось непроверенным.

## What Changes

Добавляются **процедура и каркас PoC** (fixtures + чек-лист + правила сбора evidence), но **не** production-установщик и **не** production-определения ролей. PoC доказывает:

1. **Проектную установку без изменения глобальной конфигурации Pi** — все записи только в корне и `.pi/` disposable-проекта; `~/.pi/agent/` не изменяется.
2. **Ожидаемый layout и формат ролей** — `.pi/agents/<role>.md` с frontmatter `name`/`description`/`tools`/`model` и телом инструкций; discovery через `agentScope: project`.
3. **Шесть исполнимых ролей** — черновые тестовые определения `analyst`, `architect`, `developer`, `code-reviewer`, `qa`, `devops` (fixture-качество, не production).
4. **Orchestrator как основная сессия Pi** — не файл роли; подтверждается самим фактом выполнения PoC из основной сессии.
5. **Выбор модели по контракту P2** — schema-валидный `.pi/blueprint-models.yaml` → явные `model:` для каждой роли + `defaultProvider`/`defaultModel` основной сессии.
6. **Явную обработку ошибок** — отсутствующая модель, отсутствующее/несовместимое расширение, невалидная конфигурация, permission/trust failures.
7. **Владение/конфликты/backup/повтор/восстановление** — примитивы установщика (D3) на fixtures, офлайн.
8. **Доказательство фактического вызова роли** — по JSON-событиям дочернего процесса, а не только по факту разбора файла.

**Не входит в PoC (остаётся отдельно гейтованным):** production-CLI установщика (P6b), production-определения ролей и resolver (P4), workflow-движок, sandbox/QA-runner, изменение `~/.pi/agent/`, trust или глобальной конфигурации Pi, live-запросы сверх отдельно разрешённого минимума, любые изменения в проекте скрапера криптовалют.

## Capabilities

Изменение не меняет runtime-поведения продукта: это проверочная/tooling-стадия (fixtures, процедура, отчёт). Дельты спецификаций не создаются; opt-out зафиксирован в `.openspec.yaml` через `skip_specs: true` и явно предъявляется на Gate A (конвенции: «нет изменения поведения → нет спеки»).

## Impact

- **Код:** production-код не создаётся; только fixture-ресурсы и процедура под `tests/fixtures/` и документация.
- **Зависимости:** не устанавливаются.
- **API/модели:** live-запрос только по отдельному разрешению (модель, стоимость, данные, auth).
- **Глобальная конфигурация Pi / trust:** не изменяется.
- **Смежные проекты:** скрапер криптовалют и другие проекты не затрагиваются.
- **Совместимость:** PoC фиксирует фактический контракт выбранного расширения (S3/S4), версии Pi/OpenSpec/Node и SHA-256 кандидата.
