# Design

## Context

- Pi **1.1.0**, OpenSpec CLI **1.14.0**, Node **v22.22.3** — установлены и совпадают с заявленными (`docs/compatibility.md`).
- Установленное расширение subagent `~/.pi/agent/extensions/subagent/` — это **S3** (SHA-256: `index.ts` `d7f717bc…`, `agents.ts` `e1ab7add…`), два обычных файла без package.json/README/LICENSE/Git; происхождение, версия и способ установки **не установлены** (`blocked`).
- **Кандидат S4 (предпочтительный, не подключается):**
  - Источник: `examples/extensions/subagent/` в установленном пакете `@earendil-works/pi-coding-agent@1.1.0` (Pi 1.1.0).
  - Версия: отдельного `package.json`/версии нет — привязан к релизу Pi **1.1.0**; лицензия наследует метаданные Pi (`MIT`), текста `LICENSE` в установленном пакете нет.
  - SHA-256: `index.ts` `4facaa61c9c781748dd000eb5d2ec0a75289986d1a6e11ce13971ca5653dc252`, `agents.ts` `cc85ecd33b89aa575bea3d2a9a9da7654a6305da4de02e5041aa5342a1de29b4` (сверены с `docs/compatibility.md`).
  - Совместимость с Pi 1.1.0 — **проверяемое условие** (не `verified` до PoC): discovery, передача модели/инструментов, trust/headless-поведение и побочные эффекты подлежат проверке.
- Отличия S3/S4 (verified): S4 наследует активную модель/thinking родителя при отсутствии `model` и учитывает `ctx.isProjectTrusted()`; S3 — нет. S4 принимает `tools` строкой или массивом; S3 — только строкой. Обе явно передают заданный `model`, ищут `.pi/agents` вверх от cwd, не добавляют child-флаги `--approve`/`--no-extensions`/`--no-mcp`.
- Формат роли (обе реализации): Markdown + YAML frontmatter `name`, `description` (обязательные), `tools` (необязательная строка через запятую), `model` (необязательный); тело → `--append-system-prompt`. Discovery: user `~/.pi/agent/agents/*.md` (всегда), project `.pi/agents/*.md` (только `agentScope: project|both`; `both` даёт приоритет проектным именам).
- Пользовательские агенты уже есть, но **ни одна из шести ролей blueprint не существует** ни в user-, ни в project-scope.
- `trust.json` не содержит ни `pi-pipeline-setup`, ни disposable-проекта.
- Контракт моделей P2 реализован: `schemas/model-configuration.schema.json` + fixtures `tests/fixtures/models/`.

## Goals

Доказать на disposable-проекте восемь свойств из `proposal.md` и вернуть воспроизводимый evidence-отчёт. Ничего не менять в `~/.pi/agent/`, глобальной конфигурации Pi, trust и смежных проектах.

## Non-Goals

Production-CLI установщика (P6b), production-роли/resolver (P4), workflow-движок, sandbox/QA-runner, автоматическая инициализация OpenSpec, live-запросы сверх отдельно разрешённого минимума, реализация скрапера криптовалют.

## Decisions

- **D-PoC-1 — Offline-first.** Все проверки, не требующие модельного запроса, выполняются без него: discovery, парсинг frontmatter, построение аргументов child, резолв моделей, примитивы установщика на fixtures.
- **D-PoC-2 — Две дорожки.** Track A (subagent + шесть ролей) и Track B (примитивы установщика) независимы по файлам; общий disposable-root один, но fixture-каталоги не пересекаются.
- **D-PoC-3 — Disposable-проект.** Одноразовый каталог вне рабочих проектов, без секретов и credential-файлов; baseline (список файлов + хеши) фиксируется до любых записей.
- **D-PoC-4 — Переиспользование P2.** Выбор модели идёт через schema-валидный `.pi/blueprint-models.yaml` (синтетические ID в fixture), резолв даёт явные `model:` для шести ролей и `defaultProvider`/`defaultModel` для основной сессии. Не выдумываются реальные ID и не выполняется API-запрос для резолва.
- **D-PoC-5 — Кандидат S4, без подключения.** Предпочтительный кандидат — S4 (источник/версия/SHA-256 зафиксированы выше). Подключение S4 или тестирование S3 — **отдельное разрешение**; свойства S3 и S4 не переносятся друг на друга.
- **D-PoC-6 — Evidence вызова по событиям, с разделением настроенной и фактической модели.** «Роль вызвана» доказывается JSON-событиями дочернего процесса (фактически использованная модель, фактически объявленные/использованные tools, assistant-сообщение с ответом, exit code, stopReason), а не фактом существования `.md`-файла и не полем `details.model`. Настроенная модель (`model:` / `--model`) и фактически использованная — **разные сущности**; см. раздел «Evidence вызова».
- **D-PoC-7 — Границы этапа.** Разрешены только чтение, анализ, подготовка fixture и offline-тесты. Подключение расширений, live-вызовы, изменение trust и записи вне рабочего дерева — за границей этапа, требуют отдельных разрешений.

## PoC architecture

### Track A — subagent и шесть ролей

1. Fixture-проект с `.pi/agents/{analyst,architect,developer,code-reviewer,qa,devops}.md` (черновые определения, тела по контрактам `docs/roles.md`; Reviewer/QA — `tools: read, grep, find, ls` без shell).
2. **Offline (разрешено сейчас):** discovery из корня и вложенного cwd при `agentScope: project`; парсинг frontmatter; dry-run построения аргументов child; негативы (невалидный frontmatter, пустой/некорректный `tools`, коллизия user/project имён).
3. **Live (отдельное разрешение):** один single-вызов минимальной тестовой роли с чтением синтетического `fixture.txt`; затем, при разрешении бюджета, по одному вызову на каждую из шести ролей.
4. Сбор evidence по разделу «Evidence вызова» + полный diff побочных записей.

### Track B — примитивы установщика (офлайн, fixtures)

1. Черновой формат `install-manifest` (ownership: `whole-file`, `marked-block`, `json-keys`, `frontmatter-fields`) — для PoC достаточно структуры и хешей, не полноценный D3-формат (он согласуется в P6a).
2. `plan` без записи: preview, отклонение symlink/hardlink для управляемых путей, обнаружение коллизий.
3. Применение на fixture: staging/backup/журнал внутри `.pi/blueprint/`, `current == last-applied → update`, `current == desired → no-op`, иначе — конфликт на решение.
4. **Тесты восстановления и защиты (обязательные):**
   - прерывание **между каждым шагом** установки (crash injection после каждой отдельной записи) и восстановление по journal/backup;
   - обнаружение **пользовательских изменений** управляемых файлов (drift) — не затирать чужую правку;
   - **повторная установка после частичного завершения** (manifest зафиксирован не последним / отсутствует) — блокировка или корректное продолжение, не частичный «успех»;
   - **симлинки за пределы root** — отклонение для управляемых путей;
   - **отказ в правах доступа** (permission failure) — явная ошибка, без частичного применения;
   - повторная установка неизменённого состояния = no-op.

## Evidence вызова роли (настроенная vs фактическая модель)

- **Настроенная модель:** значение `model:` во frontmatter роли и аргумент `--model`, переданный child. Это декларация, **не доказательство** фактического использования.
- **Фактически использованная модель:** устанавливается по JSON-событиям дочернего процесса (например, `message_end`/эквивалент), а не по полю `details.model` результата (оно изначально содержит запрошенную модель).
- **Фактический набор инструментов:** подтверждается тем, что child реально объявил/использовал ожидаемые имена tools; `--tools` — декларация, не граница ОС и не sandbox. Дополнительно фиксируются загруженные расширения/MCP, способные расширить фактический набор.
- **Правило приёмки:** если фактическую модель или набор инструментов нельзя достоверно подтвердить по событиям, соответствующий acceptance test считается **невыполненным** (не «пройден с оговоркой»).

## Побочные записи вне disposable-root

PoC **не изменяет существующие пользовательские данные**. Ожидаемые/потенциальные записи вне disposable-root фиксируются в таблице и проверяются до/после каждого live-теста:

| Путь | Источник записи | Назначение | Способ изоляции | Проверка до/после |
|---|---|---|---|---|
| `os.tmpdir()/pi-subagent-*/prompt-*.md` | расширение subagent (S3/S4) | передача тела роли через `--append-system-prompt` | системный temp, mode `0600`, удаляется в `finally` | baseline temp-каталога до; после — файл отсутствует (создан и удалён) |
| session/cache/log-каталоги child (`pi --no-session`) | дочерний Pi | runtime-следы child | `--no-session`, отдельный disposable `cwd`; точные пути фиксируются по событиям | diff пользовательских Pi-каталогов до/после; перечислить фактически созданные файлы |
| записи загруженных расширений/MCP child | сторонний код в child-процессе | непредсказуемое поведение | не sandbox; фиксируется перечень расширений/MCP | полный diff до/после; любая неожиданная запись — `fail` |

Любая запись вне disposable-root сверх перечисленных и согласованных — критерий `fail`, а не «известный след».

## File layout (предлагаемый, для PoC — fixture)

```text
tests/fixtures/installer-agent-role-poc/
  README.md                       # классификация всех fixture как синтетических, без секретов
  disposable/                     # одноразовый целевой проект (временный, не коммитится)
    .pi/
      agents/{analyst,architect,developer,code-reviewer,qa,devops}.md
      blueprint-models.yaml       # синтетические ModelRef
      blueprint/install-manifest.json
      blueprint/backups/<transaction-id>/
    fixture.txt                   # синтетический файл для live-чтения
  roles/                          # исходные черновые определения ролей (fixture-качество)
  installer/                      # fixture-данные для Track B (source snapshot, expected images)
```

Target-layout (для будущего production-установщика, вне PoC) остаётся как в `docs/architecture.md` §D4.

## Sequence

1. Зафиксировать baseline disposable-проекта и версии/хеши (Pi/OpenSpec/Node, кандидат S4).
2. **Offline Track A и Track B** (разрешено сейчас, без модельных запросов и записей вне рабочего дерева).
3. Отдельные разрешения (до любого live/записи вне дерева): подключение кандидата, модель/стоимость/auth, trust, допустимость temp/cache-следов.
4. Отдельно разрешённый live-read (Track A, шаг 3–4) с проверкой таблицы побочных записей.
5. Санитизированный отчёт `verified` / `not-tested` / `blocked`, отражение в `docs/compatibility.md`.
6. Предъявление независимым Reviewer и QA (обязательно оба отчёта), цикл исправлений.
7. Gate B (приёмка пользователем) и архивирование — после Gate A и реализации.

## Risks / Trade-offs

- **S3 vs S4:** S4 — предпочтительный кандидат (проверяемый источник, зафиксированные SHA-256); S3 — установлен, но происхождение неизвестно. Смягчение: явное решение пользователя + фиксация SHA-256; при несовместимости — возврат к D2, не форк.
- **Стоимость live:** доказательство шести ролей требует до шести вызовов. Смягчение: минимально один вызов для механизма, остальные — только по отдельному бюджетному разрешению.
- **Trust/headless:** child `pi --no-session` в JSON-режиме может не загрузить project settings; UI-confirmation отсутствует в headless. Смягчение: негативный тест untrusted child; отсутствие безопасного режима — блокер, не fallback.
- **Побочные эффекты:** temp prompt вне проекта, возможные session/cache-следы child. Смягчение: таблица побочных записей + полный diff до/после; неожиданная запись = `fail`.
- **Ложное «роль исполнима»:** разбор файла ≠ вызов; настроенная модель ≠ фактическая. Смягчение: D-PoC-6, правило «не подтверждено → не выполнено».

## Migration Plan

Не применимо: PoC не меняет существующий формат и не мигрирует данные. Production-миграции — в P6a/P7.
