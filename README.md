# pi-pipeline-setup

Переиспользуемый blueprint правил и ресурсов для настройки **Pi Coding Agent** в проектах.

> **Статус:** документация и архитектурные решения. Установщик, генератор конфигурации, автоматизация workflow и полноценные определения агентов **не реализованы**. Предложения, требующие согласования, перечислены в [архитектуре](docs/architecture.md).

## Назначение

Будущая настройка по ссылке на этот репозиторий должна сначала изучать целевой проект и конфигурацию Pi, показывать план файлов/моделей, получать явное согласие и только затем применять неразрушающие изменения. Пользовательские настройки и другие проекты не изменяются молча; OpenSpec не инициализируется автоматически.

## Канонические документы

- **[Workflow](docs/workflow.md)** — единственные этапы 1–10 и правила переходов; Human Gate A перед разработкой и Human Gate B перед архивированием обязательны. Это инструкции процесса, не готовый workflow-движок.
- **[Роли](docs/roles.md)** — основной источник контрактов: `orchestrator` (главная сессия Pi), `analyst`, `architect`, `developer`, `code-reviewer`, `qa`, `devops` (будущие subagents). Действия OpenSpec не превращаются в роли; `explore` необязателен.
- **[Модели](docs/model-configuration.md)** — логические уровни `cheap / medium / expensive`, профили **Economy / Balanced / Quality**, проектные/ручные overrides. Пользователь сопоставляет уровни реальным provider/ID; Pi сам не классифицирует стоимость. Модель основной сессии и модели subagents настраиваются раздельно.
- **[Архитектура](docs/architecture.md)** — проверенные механизмы Pi/OpenSpec, происхождение расширения и шесть решений со статусом `requires-user-approval`.
- **[План реализации](docs/implementation-plan.md)** — небольшие проверяемые этапы, зависимости и точки согласования; не разрешение на реализацию.
- **[Установка](install/README.md)** и **[сценарий](install/scenario.md)** — будущая безопасная процедура, не готовая команда установки.

## Принципы

Общие правила не предполагают конкретный стек. Контракты ролей не зависят от провайдера/модели. Будущие ресурсы должны реализовывать канонические документы, а не дублировать их независимо.

Отдельный контекст subagent не изолирует файлы. Reviewer/QA по умолчанию не получают оболочку; безопасное исполнение тестов требует отдельной среды либо ручного запуска с логами. Подробности: [agents/README.md](agents/README.md).

## Дальнейшая работа — только после согласования

Порядок дальнейшей работы определён в [плане P0–P8](docs/implementation-plan.md), а не отдельным списком в README.

- **P0:** согласовать решения **D1–D6** из [архитектурного предложения](docs/architecture.md); все пока имеют статус `requires-user-approval`.
- **Следующий технический этап после P0 — P1:** проверить предпосылки и подготовить матрицу совместимости и протокол PoC, без установки/подключения расширения и модельных запросов.
- Полноценные определения шести subagents предусмотрены только в **P4**, после проверки совместимости и успешного PoC одной тестовой роли в **P3**. Проектирование установщика **P6a** отделено от реализации **P6b**.

Согласование архитектуры не разрешает автоматически приступать к реализации: live-запросы, установка/подключение расширения, изменение trust и применение конфигурации требуют отдельных согласований. Установщик и workflow-движок не реализованы; Human Gates задаются инструкциями, а не техническими блокировками.
