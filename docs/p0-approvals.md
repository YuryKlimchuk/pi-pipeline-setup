# Утверждение решений P0 (D1–D6)

> **Дата утверждения:** 2026-10-11 (11:28 UTC, +03:00).
> **Статус:** `approved` ровно для шести решений D1–D6, перечисленных ниже.
> Это запись принятия решений, а не новая архитектура и не разрешение на реализацию.

## Основание

Явное поручение пользователя в текущей сессии по репозиторию `pi-pipeline-setup`: утвердить перечисленные архитектурные решения D1–D6 и выполнить P1 (статическое техническое исследование + подготовка протокола PoC) в рамках заявленных ограничений.

Поручение является явным разрешением утвердить именно эти шесть решений и провести статическое исследование P1. Оно **не разрешает**: реализацию системы, установку или подключение расширений, установку зависимостей, live-запросы к моделям, выполнение аутентификации, изменение trust/permissions/глобальной конфигурации Pi, запуск непроверенного внешнего кода, создание полноценных определений ролей, реализацию генератора/установщика/workflow engine, создание модельных YAML для рабочего проекта, выполнение PoC, Git commit/push.

## Область утверждения

Утверждаются **только** шесть решений D1–D6 в формулировках ниже. Не утверждаются автоматически:

- остальные предложения, этапы реализации (P2–P8), будущие технические предположения;
- конкретные пути, schema, manifest и имена полей, если они явно не вошли в формулировки ниже и не согласованы отдельно;
- выбор конкретной реализации/библиотеки установщика или генератора.

Утверждение не изменяет статус остальных предложений: они остаются `proposed`/гипотезами до отдельного согласования.

## Принятые решения

### D1 — Model configuration — `approved`

Два декларативных источника с разными обязанностями:

- blueprint-пресеты задают абстрактные tiers и назначения ролей без конкретных model ID;
- проектная конфигурация задаёт конкретные `provider/model-id` и разрешённые overrides.

Применение конфигурации явное: preview, проверка конфликтов, подтверждение пользователя. Без watcher и автоматического применения. Модельные YAML для рабочего проекта в рамках P1 не создаются.

### D2 — Subagent — `approved`

Утверждается проверенное внешнее предусловие для subagent-интеграции.

Пример subagent из Pi 1.1.0 считается **кандидатом для исследования**, а не подтверждённой зависимостью и не выбранной реализацией. В P1 изучается его контракт, происхождение, версия, лицензия, технические ограничения и пригодность. Расширение не устанавливается и не подключается.

### D3 — Installer — `approved`

Проектное копирование фиксированной версии файлов с manifest и учётом ownership.

Минимальная версия будущего установщика предусматривает: preview изменений; обнаружение конфликтов с пользовательскими файлами; backup; безопасное восстановление; идемпотентное обновление; явное подтверждение применения.

Для будущего v1 приняты Linux и обычная локальная файловая система как исходная целевая платформа для проектирования и проверки. Это не разрешение реализовывать установщик в P1.

Предлагаемый каталог backup: `.pi/blueprint/backups/`. Backup доступен пользователю, имеет ограниченные права доступа, не очищается автоматически и не добавляется в Git автоматически. Ограничения и вопросы безопасности такого решения фиксируются в P1.

### D4 — Instructions — `approved`

- управляемый блок инструкций в корневом `AGENTS.md`;
- справочные документы blueprint в `.pi/blueprint/`;
- обнаружение конфликтов контекста до применения изменений;
- остановка установки при неоднозначных конфликтах.

`SYSTEM.md` и `APPEND_SYSTEM.md` не заменяются автоматически; сохранение других файлов инструкций не предполагается гарантирующим прежнее поведение.

### D5 — QA — `approved`

QA v1 без собственного test runner и без произвольного выполнения shell-команд. QA поддерживает:

- независимый статический анализ;
- анализ результатов ручных тестов и существующего CI;
- проверку предоставленных логов с привязкой к редакции проверяемых артефактов;
- явное указание непроверенных критериев и ограничений evidence.

Статический анализ не выдаётся за выполненные runtime-тесты.

### D6 — Approvals and evidence — `approved`

- журнал согласований в рамках сессии;
- запись существенных согласований в `proposal.md`;
- привязка согласований к редакциям артефактов;
- переносимые evidence;
- фиксация результата архивирования OpenSpec.

В evidence не попадают секреты и ненужные персональные данные. Автоматическая очистка evidence не допускается. Требования к доступу и хранению документируются.

- OpenSpec CLI **1.14.0** (`openspec --version`), пакет `@fission-ai/openspec@1.14.0`: license `MIT`, файл `LICENSE` присутствует, `repository` `https://github.com/Fission-AI/OpenSpec`.
- Node **v22.22.3**.
- Subagent-кандидат S4 (`examples/extensions/subagent/{index.ts,agents.ts}` из Pi 1.1.0) — статический контракт и SHA-256 совпадают с ранее записанными (см. [compatibility.md](compatibility.md)).
