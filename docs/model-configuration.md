# Конфигурация моделей по ценовым уровням

> **Статус:** это **наша логическая конфигурация**, а не встроенная функция Pi. Pi не предоставляет готовой классификации моделей по стоимости. Уровни `cheap` / `medium` / `expensive` — абстракция blueprint, которая при установке сопоставляется с реальными моделями, доступными в конкретном окружении Pi.

## Что реально поддерживает Pi (проверено)

| Механизм | Что делает |
|---|---|
| `model:` во frontmatter subagent (`agents/README.md`) | Назначает модель конкретному агенту; если поле опущено — используется модель по умолчанию. |
| `defaultModel` / `defaultProvider` в `settings.json` | Модель по умолчанию для новых сессий. |
| `pi --list-models [search]` | Выводит доступные модели (проверка доступности). |
| `/model` (интерактивно) | Выбор модели; picker показывает модели с доступной аутентификацией. |
| `modelThinkingLevels`, `enabledModels` | Дополнительные настройки уровня размышлений и цикла моделей. |

**Вывод:** назначать модель агенту можно; классифицировать модели по цене — нет. Поэтому `cheap/medium/expensive` — это **наши ключи конфигурации**, а не свойство модели в Pi.

## Разделение понятий (не смешивать)

| Понятие | Где хранится | Что содержит |
|---|---|---|
| Роль и инструкции агента | `.pi/agents/<role>.md` (тело + frontmatter без `model`) | Назначение, вход/выход, запреты, формат вывода |
| Модель агента | конфигурация blueprint → разрешается в `model:` frontmatter | Конкретный ID модели |
| Доступные инструменты | `tools:` frontmatter | Список инструментов (наименьшие привилегии) |
| Параметры запуска subagent | вызов инструмента `subagent` (single/parallel/chain, `agentScope`) | Режим, контекст, `{previous}` |
| Этапы workflow | `docs/workflow.md`, `workflow/orchestrator.md` | Когда и какую роль запускать |

Инструкции агента **не содержат** `model`. Смена модели не требует правки инструкций.

## Ценовые уровни

| Уровень | Когда применять |
|---|---|
| `expensive` | Наиболее сложные задачи: качество рассуждений и архитектурных решений критично. |
| `medium` | Хороший анализ и стабильное качество при умеренной стоимости. |
| `cheap` | Типовые, узкие, хорошо формализованные задачи. |

## Начальная гипотеза распределения

| Роль | Уровень | Обоснование |
|---|---|---|
| `orchestrator` | expensive | Управляет процессом, разрешает неоднозначности, принимает решения о переходах |
| `analyst` | medium | Анализирует требования и выявляет пробелы |
| `architect` | expensive | Проектирует решение и оценивает компромиссы |
| `developer` | medium | Реализует задачи по согласованному плану |
| `code-reviewer` | expensive | Независимо ищет сложные дефекты и архитектурные проблемы |
| `qa` | medium | Анализирует сценарии, критерии приёмки и тестирование |
| `devops` | medium | Решает инфраструктурные и конфигурационные задачи |

Это **стартовая рекомендация**, а не жёсткое правило.

## Когда уровень можно понизить или повысить

**`developer` → `cheap`**, когда задача механическая и хорошо формализована: шаблонный CRUD, простой баг-фикс, правки по детальному `tasks.md` без проектных решений.
**`developer` → `expensive`**, когда: сложные алгоритмы, конкурентность, безопасность, работа с legacy-кодом без тестов, или задача требует самостоятельных проектных решений.

**`qa` → `cheap`**, когда: поверхностный smoke-прогон регрессий по уже покрытому коду, критерии приёмки полностью формализованы.
**`qa` → `expensive`**, когда: анализ безопасности/производительности, сложные негативные/граничные сценарии, размытые критерии приёмки.

**`devops` → `cheap`**, когда: тривиальная проверка конфигурации без изменений.
**`devops` → `expensive`**, когда: проектирование/отладка сложного CI/CD, контейнеризации, инфраструктурных миграций.

**`analyst` → `cheap`**, когда требования уже точны (нужно лишь структурировать); **→ `expensive`**, когда домен неоднозначен или высокие ставки.
**`code-reviewer` → `medium`** для маленьких сфокусированных диффов; **`expensive`** для широких/сложных изменений.

Решение о повышении/понижении принимает **оркестратор** (или пользователь) на этапе планирования, исходя из сложности задачи.

## Профили

Профиль — это пресет назначений уровня для ролей. Стартовые варианты:

| Роль | `economy` | `balanced` (по умолчанию) | `max-quality` |
|---|---|---|---|
| orchestrator | medium | expensive | expensive |
| analyst | cheap | medium | expensive |
| architect | medium | expensive | expensive |
| developer | cheap | medium | expensive |
| code-reviewer | medium | expensive | expensive |
| qa | cheap | medium | medium |
| devops | cheap | medium | medium |

Профиль выбирается при установке; любое назначение можно переопределить для конкретной роли и конкретного проекта.

## Механизм настройки

Конфигурация трёхслойная (наше проектное решение; реализуется на этапе установщика):

1. **Blueprint-по-умолчанию** — `config/models.yaml` в этом репозитории: определение уровней, профили и маппинг `роль → уровень`. Без конкретных ID моделей.
2. **Переопределение проекта** — файл в целевом проекте (предлагаемое имя `.pi/blueprint-models.yaml`, TBD): маппинг `уровень → реальный ID модели` и персональные переопределения ролей. Единственное место, где появляются конкретные модели.
3. **Сгенерированные файлы агентов** — установщик разрешает уровни в конкретные ID и записывает их в `model:` frontmatter `.pi/agents/<role>.md` (или оставляет `model` отсутствующим, чтобы агент наследовал модель по умолчанию).

### Сценарии настройки

- **Выбор модели по умолчанию.** Роль без явного `model:` наследует `defaultModel` из `settings.json`. Оркестратор (основная сессия) использует модель, выбранную пользователем.
- **Настройка модели для роли.** В переопределении проекта указать `роль → уровень` (или напрямую `роль → ID модели`).
- **Переопределение для конкретного проекта.** Только файл проекта меняет маппинг; blueprint-по-умолчанию не трогается.
- **Смена модели без изменения инструкций.** Меняется только `model:` frontmatter (или маппинг в файле проекта) — тело агента и его роль не меняются.
- **Проверка доступности перед установкой.** Установщик проверяет каждую конкретную модель через `pi --list-models <pattern>` и сообщает о недоступных, не записывая их молча.
- **Выбор профиля.** `economy` / `balanced` / `max-quality` — пресет; после выбора допускаются точечные переопределения.

> Конкретные ID моделей здесь **намеренно не указаны** — они зависят от окружения и разрешаются при установке.
