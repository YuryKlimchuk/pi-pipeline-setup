# Конфигурация моделей

> **Статус:** архитектурное предложение. Конфигурационный файл, генератор и установщик отсутствуют. Pi не читает YAML blueprint и не классифицирует модели как `cheap`, `medium`, `expensive`.

## Основная сессия и subagents — разные механизмы

| Назначение | Существующий механизм |
|---|---|
| Модель по умолчанию основной сессии (`orchestrator`) | `defaultProvider` и `defaultModel` в проектном `.pi/settings.json` (после доверия проекту); пользовательские defaults остаются нетронутыми |
| Ручной выбор основной модели | `pi --model <provider/model-id>` для запуска или `/model` внутри сессии. Возобновляемая сессия может восстановить прежний выбор; изменение defaults не переключает её автоматически |
| Модель отдельной роли subagent | Поле `model:` в определении роли передаётся расширением как `--model`. Для каждой из шести ролей предлагается явный полный `provider/model-id` |
| Инвентарь моделей | `pi --list-models [search]`; `/model` показывает модели с доступной аутентификацией. Поиск может быть нечётким — нужно сверять точную пару provider + ID |

**Orchestrator не subagent:** файла `.pi/agents/orchestrator.md` и его поля `model:` не предполагается. Смена `/model` в основной сессии не переназначает модели ролей.

В установленном локальном расширении при отсутствии `model:` аргумент `--model` не передаётся: дочерний Pi выбирает модель по своим startup settings и правилам доступности, а не гарантированно по активной модели Orchestrator. Поставляемый с Pi пример расширения описывает другое поведение — наследование активной модели/уровня размышлений. Поэтому поведение нужно сверять с выбранной реализацией расширения; blueprint **не полагается на неявное наследование**. См. [источники проверки](architecture.md).

## Идентификаторы и ценовые уровни

- `cheap` — дешёвая модель для узких, хорошо формализованных задач.
- `medium` — модель средней стоимости для обычной разработки и анализа.
- `expensive` — дорогая модель для сложных решений и повышенных рисков.

Это относительные бюджетные категории, не параметры Pi, не thinking levels и не гарантия качества. Каталожные цены могут служить справкой, но подписки, кэширование, длина контекста и условия провайдера меняют фактическую стоимость. **Пользователь задаёт или подтверждает соответствие уровней реальным моделям**, а не получает выдуманные ID или автоматически «достоверную» классификацию. Допустима одна модель на несколько уровней, если пользователь это подтвердил.

## Профили и начальная рекомендация

Названия профилей едины: **Economy**, **Balanced**, **Quality**. Balanced — исходная рекомендация, не неизменяемое правило.

| Роль | Economy | Balanced (по умолчанию) | Quality |
|---|---|---|---|
| `orchestrator` | medium | expensive | expensive |
| `analyst` | cheap | medium | expensive |
| `architect` | medium | expensive | expensive |
| `developer` | cheap | medium | expensive |
| `code-reviewer` | medium | expensive | expensive |
| `qa` | cheap | medium | expensive |
| `devops` | cheap | medium | expensive |

Дешёвой модели достаточно для простой реализации по точному плану, типовых тестов с известными ожиданиями, небольших исправлений и несложных конфигурационных задач. Это не повод пропускать независимые проверки или gates. Размытые требования сначала уточняют, а не просто отправляют более дорогой модели.

Сложные алгоритмы, конкурентность, безопасность, миграции, legacy без тестов, широкие изменения и сложные негативные сценарии оправдывают medium/expensive. Для небольшого diff Reviewer может использовать medium. Orchestrator предлагает изменение уровня с обоснованием; пользователь может вручную выбрать точную модель. Сложность не разрешает Developer самовольно менять архитектуру или scope.

## Единый источник конфигурации — предложение на согласование

Сейчас каталога `config/` нет. Создавать `config/models.yaml` ради ранее упомянутого пути не нужно: в репозитории ещё нет исполняемого потребителя. Предлагается следующий **будущий** вариант:

| Источник | Содержимое | Статус |
|---|---|---|
| Этот документ | Канонические профили и рекомендации, пока нет реализации | Существует |
| `config/models.yaml` в blueprint | Версия формата, выбранный по умолчанию профиль и назначения `роль → уровень` для профилей; без конкретных моделей | Планируется только после согласования формата/генератора |
| `.pi/blueprint-models.yaml` в целевом проекте | Версия формата и blueprint, выбранный профиль, полное сопоставление `уровень → provider/model-id`, проектные назначения ролей и отдельный выбор основной сессии | Предлагаемый единый редактируемый источник конкретных назначений; пока отсутствует |
| `.pi/settings.json` и `.pi/agents/<role>.md` | Производные runtime-настройки Pi, а не второй независимо поддерживаемый каталог назначений | Будущий результат применения |

Обоснование: декларативный проектный источник отделяет бюджетную политику от инструкций и пользовательских настроек Pi; версия blueprint фиксирует исходные пресеты. YAML удобен для обзора, но это **не нативный формат настройки Pi** и пока не утверждённый контракт парсера. Секреты в него не записываются. `models.json` Pi регистрирует провайдеры/модели и не заменяется этим файлом.

### Порядок разрешения (будущий контракт)

1. Взять назначения выбранного профиля из зафиксированной версии blueprint.
2. Для основной сессии применить проектное назначение `orchestrator`; для каждого subagent — его проектное переопределение. Одно назначение выбирает **либо уровень, либо точную модель**, не оба сразу; неизвестные роли/уровни и отсутствующие соответствия считаются ошибкой.
3. Разрешить уровни через подтверждённое проектное сопоставление. При необходимости изменить только одну роль, не меняя модель всех пользователей уровня.
4. Ручное назначение конкретной модели имеет приоритет для согласованной роли/запуска. Постоянный выбор сохраняется в проектном источнике; временный выбор фиксируется отдельно и не выдаётся за изменение профиля.
5. Показать таблицу «роль → профиль → override → итоговый provider/ID», проверить её, запросить подтверждение записи.

Для основной сессии результат раскладывается на `defaultProvider`/`defaultModel`. Для **всех шести** subagents результат записывается явным `model:`. Тела инструкций остаются провайдер-независимыми. Не предполагаются ни live-чтение YAML агентами, ни watcher, ни автоматическое переключение по сложности.

### Применение после установки и ручные изменения

Будущий генератор должен повторять цикл «прочитать источник и существующие файлы → вычислить назначения → проверить → показать diff → получить согласие → применить». Неизвестные ключи `settings.json`, тела агентов и пользовательские изменения сохраняются. Расхождение с ранее сгенерированным результатом — конфликт для решения пользователем, а не повод перезаписать файл.

Пока генератора нет, эти операции выполняются только вручную по согласованному плану. Изменение YAML само по себе ничего не применяет. Defaults основной сессии проверяются в новом запуске; в текущем используется `/model`. Локальное расширение перечитывает определения агентов при следующем вызове. `/reload` нужен для изменённых ресурсов Pi, но не компилирует YAML и не гарантирует смену активной модели.

У текущего инструмента `subagent` **нет параметра модели на отдельный вызов**. Ручной override для него требует согласованной правки `model:` с отражением в источнике (либо документированной временной правки и последующего восстановления). Другой вариант — отдельный ручной запуск Pi с `--model` и инструкцией роли; это не скрытая функция `subagent`.

## Проверка доступности и отказ

- До записи и после смены окружения сверить точные provider/ID с `pi --list-models`, проверить настройки и аутентификацию без вывода секретов. В Pi 1.1.0 доступен `pi auth check --model <provider/model-id> --json --no-refresh`; не использовать вывод credentials.
- Наличие в каталоге/аутентификация не доказывают доступность API, квоту или пригодность модели для инструментов. Пробный запрос возможен только с отдельного согласия на отправку данных и стоимость; в отчёте различать «найдена», «auth готова», «запрос проверен» и «не проверено».
- Если модель исчезла или запрос не работает, остановить затронутый запуск, сообщить ошибку и предложить доступные варианты. **Никакой молчаливой подмены** модели, провайдера или уровня.
- Пользователь подтверждает замену, после чего источник и runtime-файлы согласованно обновляются и проверяются. Неудачная проверка не должна оставлять частично применённую конфигурацию.
