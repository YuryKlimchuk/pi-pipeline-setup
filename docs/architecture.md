Репозиторий — blueprint правил и ресурсов для Pi, сейчас **документация, конвенции и справочные шаблоны**. Здесь нет установщика, workflow-движка, генератора моделей или полноценных определений агентов.

## Основание технических утверждений

Проверено по локально установленным **Pi 1.1.0** и **OpenSpec CLI 1.14.0**:

- документация пакета `@earendil-works/pi-coding-agent`: `docs/configuration.md`, `settings.md`, `models.md`, `cli.md`, `extensions.md`, `security.md`, `containerization.md`, `skills.md`, `prompt-templates.md`, `packages.md`;

- `openspec --help`, справка `init`, `validate`, `archive`, `instructions` и установленная схема `schemas/spec-driven/schema.yaml` пакета `@fission-ai/openspec`.

Это пути **внешней установки**, не файлы этого репозитория. Публичные источники: [Pi](https://github.com/earendil-works/pi), [OpenSpec](https://github.com/Fission-AI/openspec). Для целевого окружения нужно повторно сверить версии и выбранное расширение. Нельзя переносить свойства одного subagent-расширения на все реализации.

## Существующие механизмы

### Pi

- `.pi/settings.json` задаёт проектные настройки; после доверия проекту они перекрывают пользовательские, списки ресурсов объединяются. Это runtime-семантика Pi, **не готовый алгоритм безопасного слияния файлов установщиком**.
- `.pi/APPEND_SYSTEM.md` добавляет инструкции, `.pi/SYSTEM.md` заменяет системный промпт. Проектные файлы имеют приоритет над одноимёнными пользовательскими, а не объединяются с ними. Установка не должна молча вытеснять пользовательские инструкции.
- Контекст `AGENTS.md`/`CLAUDE.md` обнаруживается от рабочего каталога вверх и в пользовательском каталоге; `AGENTS.override.md` заменяет контекст того же каталога. Эти инструкции не требуют project trust. **`.pi/AGENTS.md` не следует считать автоматически загружаемым при запуске из корня проекта**; предлагается корневой `AGENTS.md`.
- `.pi/skills/`, `.pi/prompts/`, `.pi/extensions/` — проектные ресурсы с правилами доверия. Prompt template раскрывает текст, не исполняет переход workflow. Skill загружается по требованию; поле `allowed-tools` не следует выдавать за sandbox.
- Модель основной сессии задаётся defaults, CLI или `/model`; настройки конкретных моделей/провайдеров не являются уровнями стоимости blueprint.
- Extension API позволяет блокировать tool calls и запрашивать подтверждения. Blueprint таких обработчиков не содержит. Расширения выполняются с правами процесса; project trust и tool selection не заменяют изоляцию ОС.
- Pi-пакеты распространяют extensions/skills/prompts/themes. `agents/` не является стандартным типом ресурса package manifest; его доставку и обнаружение нужно решать отдельно.

### Проверенное локальное расширение subagent

- Не встроено в Pi и не поставляется этим blueprint. Запускает дочерний `pi --mode json -p --no-session`, добавляет тело роли через `--append-system-prompt`, `model` через `--model`, непустой `tools` через `--tools`.
- Поддерживает single/parallel/chain с `{previous}`. Parallel: до 8 задач, до 4 одновременно; видимый модели финальный вывод ограничивается 50 KiB на задачу, полные результаты остаются в details. Это не общий лимит всех режимов.
- Изолирует контекст, не файловую систему. Ищет ближайший `.pi/agents/` вверх до корня файловой системы. Default scope — `user`, проектный включается явно; `both` отдаёт приоритет проектным именам.
- При пропущенном `model` **не передаёт активную модель родителя**. README поставляемого примера обещает наследование активной модели и thinking level — локальная реализация отличается. Поэтому требуются явные модели и фиксация совместимой реализации перед поставкой.
- Локальная реализация спрашивает подтверждение проектных агентов при наличии UI; без UI этот вопрос не обеспечивается. Дочерний процесс не получает `--approve`, `--no-extensions` или `--no-mcp`. Выбор `agentScope`/подтверждение агента не гарантирует загрузку project settings дочерним Pi.
- Нет параметров вызова для динамического выбора модели, sandbox, read-only shell или бизнес-gates. Подробности безопасного применения: [agents/README.md](../agents/README.md).

### OpenSpec

- CLI поддерживает Pi (`openspec init --tools pi`), артефакты, зависимости, статус, validation и archive. В Pi сгенерированные команды используют имена `/opsx-…` по именам prompt-файлов; конкретный набор зависит от профиля/версии.
- Схема `spec-driven`: `proposal → (specs, design) → tasks`; apply требует tasks и отслеживает чек-боксы. Это состояние артефактов, не доказательство согласия пользователя.
- Blueprint требует краткий `design.md` даже для простого изменения и сохраняет корректный OpenSpec opt-out `skip_specs` только без изменения поведения, явно согласуемый на Gate A.
- Перед любой записью проверяется фактический planning root: CLI может разрешить внешний store или корень родительского проекта. Запись вне согласованного целевого проекта требует отдельного разрешения.
- Инициализация — только явное решение пользователя, не часть автоматической установки. `new change` также может создать корень; отсутствие корня должно блокировать этот обход.
- Команды из старых пользовательских skills вроде `openspec generate` или `openspec update-version` отсутствуют в проверенном CLI; такие skills нельзя копировать без сверки.

## Исходные вопросы до реализации

1. **Конфигурация моделей:** предложены будущие `config/models.yaml` (профили без ID) и `.pi/blueprint-models.yaml` (проектный источник конкретных назначений), явная генерация `model:` для шести ролей и defaults основной сессии. Утвердить расположение, версионирование формата и приоритеты из [модельного документа](model-configuration.md).
2. **Зависимость subagent:** выбрать проверенную реализацию/версию и способ доставки — предусловие, отдельный пакет или поставляемая копия. До этого нельзя гарантировать наследование моделей, доверие дочерней сессии или инструменты.
3. **Доставка и обновления:** выбрать копирование по сценарию или Pi-пакет; определить учёт сгенерированных файлов, обнаружение пользовательских правок, резервные копии/откат и идемпотентное слияние. Рекомендуется проектная область, без глобальной установки по умолчанию.
4. **Подключение инструкций:** предлагается согласованное дополнение корневого `AGENTS.md` и доставка необходимых справочных документов с рабочими ссылками, а не одиночное копирование `rules/AGENTS.md` с битыми путями. Конкретный layout устанавливаемой документации предстоит утвердить.
5. **Исполняемое QA:** по умолчанию статическое чтение и анализ логов. Утвердить внешний CI/ручной запуск или изолированный runner для тестов; никаких обещаний read-only при наличии shell.
6. **Устойчивое хранение согласований:** сейчас инструкция требует явного подтверждения и записи редакции. Отдельный журнал/формат согласований и технические блокировки gates — возможная будущая работа, не реализованный механизм.

Канонические роли, этапы и обязательные Gate A/B заданы требованиями проекта и не являются опциональными пунктами этого списка. Реализация перечисленных решений начинается только по дальнейшему согласованию.

S3 этого не делает: tools разбираются как строка, некорректный тип может сорвать обнаружение. Это запись вне проекта при **запуске**, не часть установки; PoC должен отдельно согласовать temp/cache/session следы. Поле результата `model` первоначально содержит запрошенную модель, поэтому оно само по себе не доказывает фактически использованную: проверять события дочернего процесса.

### Что уточняется, не меняя согласованных требований

1. **Новый `AGENTS.md` может скрыть существующий `CLAUDE.md`** (S5). Ранее требование «сохранить файл» не покрывало сохранение его действия. D4 предлагает проверять эффективный контекст и блокировать конфликт, а не молча создавать точку входа.
2. **Project trust родителя не гарантирует загрузку настроек child** (S2–S4). В JSON без сохранённого решения/обработчика/CLI override при `ask` настройки пропускаются. D2 требует отрицательного теста и отдельного решения пользователя о доверии, а не автоматического `--approve`.
3. **Временный override subagent не существует как параметр вызова** (S3/S4). D1 оставляет постоянное назначение через проектный источник, а разовый выбор — отдельной явно согласованной операцией, не выдуманным API.
4. **Журнал Gate A может менять хеш самого proposal.** D6 задаёт исключение только служебного раздела журнала из снимка; это уточнение фиксации редакции, не отмена повторных gates.

### D1. Конфигурация моделей

**Статус:** `approved` (утверждено 2026-10-11, см. [p0-approvals.md](p0-approvals.md)).

**Проблема и ограничения.** Нужны переиспользуемые профили без provider ID и проектные назначения без семи независимо редактируемых копий. Pi понимает settings/frontmatter, но не YAML blueprint (S2–S4). Канонические профили и приоритеты остаются в [модельном документе](model-configuration.md); здесь уточняется их будущий формат.

| Вариант | Плюсы | Минусы и сопровождение |
|---|---|---|
| Только runtime-файлы, профили в документации | Нет парсера/генератора, простая ручная настройка | Семь назначений легко расходятся; смена профиля ручная. Низкая стоимость старта, высокая повторная проверка |
| Один проектный YAML, профили встроены в генератор | Один пользовательский файл, меньше ресурсов | Бюджетная политика спрятана в коде; менять её приходится релизом кода. Средняя стоимость |
| Два YAML: пресеты blueprint + проектные назначения | Разделение общей политики и конкретных ID, воспроизводимые версии | Нужны schema validation, pin и проверка drift. Средняя стоимость, рекомендуемый вариант |

**Рекомендация и конкретный формат v1.** Оба YAML оправданы при появлении генератора: общий файл не второй источник конкретных моделей, а версионированная библиотека профилей. До генератора их не создавать. YAML ограничить JSON-совместимыми типами, запретить duplicate keys, custom tags, merge keys и aliases; неизвестные поля/версии — ошибка, не игнорирование.

| Файл / поля | Тип и контракт |
|---|---|
| `config/models.yaml`: `schemaVersion` | Целое `1` |
| `defaultProfile` | Enum `Economy`, `Balanced`, `Quality`; начальное значение `Balanced` |
| `levels` | Ровно список `cheap`, `medium`, `expensive` |
| `profiles.<profile>.roles.<role>` | Полная карта семи канонических ролей в уровень; значения строго из таблицы модельного документа, без ID провайдера |
| `.pi/blueprint-models.yaml`: `schemaVersion` | Целое `1` |
| `blueprint.revision`, `blueprint.presetsSha256` | Неизменяемый commit/release digest blueprint и хеш байтов пресетов; не плавающая ветка/`latest` |
| `profile` | Обязательный enum трёх профилей; default подставляется только при первом согласованном создании |
| `levels.<level>` | Все три значения — объект `ModelRef`: непустые строки `provider`, `id`; ID хранится целиком, в том числе `/` и `:` |
| `orchestrator` | Необязательный `Assignment`, только основной session default |
| `subagents.<role>` | Необязательные overrides только для шести subagents; `orchestrator` здесь запрещён |
| `Assignment` | Ровно одно: объект с `level` либо объект с `model: ModelRef`; отсутствие назначения означает профиль, не пустую модель |

Профили не дублировать в проектном YAML. Установка сохраняет неизменяемый снимок пресетов в `.pi/blueprint/config/models.yaml` с тем же хешем; это **производный ресурс**, не редактируемый третий источник. Обновление pin и пресетов — только отдельный diff. Потерянный/изменённый снимок блокирует генерацию до восстановления из точной версии. В будущих тестах таблица профилей документации должна сверяться с пресетами, чтобы не поддерживать две разные политики.

Разрешение: профиль → `orchestrator`/`subagents` override → сопоставление уровня → итоговый `ModelRef`. Постоянный ручной выбор означает изменение соответствующего override в проектном YAML и повторное применение. Для основной сессии временный `/model`/CLI не меняет источник; resume может вернуть прежнюю модель. Для subagent v1 предпочитает постоянный override; разовый запуск Pi с явно выбранной моделью и инструкцией роли допустим отдельно. Временная правка frontmatter, если пользователь её выбрал, требует записи исходного значения, согласования и восстановления; при незавершённом восстановлении обнаруживается drift, а не новый default.

Генератор записывает только `defaultProvider/defaultModel` и шесть явных `model: provider/id`. Нельзя делить ID по каждому `/` или интерпретировать его как shell-строку; точное разрешение CLI, включая ID с `:`, проверяется в PoC. Никаких thinking/budget/API-ключей в schema v1. Тела ролей и прочие ключи settings не принадлежат генератору моделей.

**Как исключать расхождение.** Manifest D3 хранит хеш источника, pin пресетов, версию генератора и последний применённый результат по управляемым полям. Перед применением сравниваются source / previous generated / current runtime. Если runtime не менялся — показать новый diff; если менялся — остановиться. Пользователь выбирает импорт точной runtime-модели в override либо восстановление из источника; любое решение показывается единым планом и применяется совместно. Нет watcher и автоматического обратного импорта. Проверка drift перед запуском предписана Orchestrator, но без движка не перехватывает прямой запуск Pi.

**Доступность и ошибки.** Проверить точную пару в каталоге и безопасный auth-status без refresh/credentials (S2); произвольные credential commands и provider extensions сначала исследовать, не выполнять вслепую. Статусы отчёта отдельно: `catalog-found`, `auth-ready`, `request-verified`, `not-checked`, с окружением/временем. Live-запрос и расходы только по отдельному разрешению. При неизвестном ID, auth/API-ошибке, неподдерживаемой schema или drift — остановка затронутой настройки/запуска, без fallback и частичного применения. Обновление каталога/провайдера тоже не побочный эффект.

**Влияние:** нужен чистый resolver/validator, генерация патчей, тесты приоритетов и конфликтов, связка с транзакцией D3. Альтернативы не запрещены навсегда, но runtime-only не даёт воспроизводимости, а кодовые пресеты хуже обозримы.

**Риски / пересмотр:** цена не равна качеству; catalog/auth не гарантируют запрос; CLI может неоднозначно трактовать ID. При появлении нативных пресетов Pi или необходимости сложных per-run overrides пересмотреть schema, а не расширять молча. **Локально:** можно проверить schema и resolver на фиктивных ModelRef без запросов, затем реальные ID в согласованном окружении. **Пользователь:** утверждает формат, профиль, реальные назначения и разрешения на платные проверки.

### D2. Зависимость subagent

**Статус:** `approved` (утверждено 2026-10-11, см. [p0-approvals.md](p0-approvals.md)).

**Проблема и ограничения.** S3 не имеет установленного происхождения/версии и не может стать переносимым контрактом только потому, что загружен у автора. S4 — проверяемый исходный пример конкретного релиза, но не обещание стабильного API. Runtime-совместимость ещё не проверена.

| Вариант | Плюсы | Минусы и сопровождение |
|---|---|---|
| Предустановленное проверенное расширение | Ничего не устанавливать за пользователя; минимальная v1 | Больше предварительных действий, контроль хешей и окружения. Низкая поставка, средняя стоимость compatibility tests |
| Отдельный совместимый Pi-пакет с точным pin | Удобная доставка и обновления, отдельный lifecycle | Конкретный пакет пока не выбран/не проверен; supply-chain, загрузка кода и зависимости. Средняя стоимость аудита и тестов |
| Собственная копия/форк | Контроль child args, обнаружения и диагностики | Ответственность за безопасность, lifecycle, upstream diff, лицензию и релизы. Высокая постоянная стоимость |

**Рекомендация:** для v1 — внешнее предусловие с проверяемым compatibility descriptor; кандидат для PoC — **пример S4 из Pi 1.1.0**, а не неизвестная копия S3. Сейчас не копировать/подключать его и не заменять существующий инструмент. После успешного PoC зафиксировать Pi/OpenSpec/Node, источник релиза, хеши обоих файлов, платформу и результаты тестов. Другая версия/хеш — `unsupported/unverified`, не автоматическое принятие. Отдельный пакет можно принять позже после аудита; именовать несуществующий пакет сейчас нельзя.

Минимальный поддерживаемый контракт: single-вызов с `agentScope: project`; обнаружен ожидаемый canonical project path; `name/description/model` — строки, `tools` — непустая строка известных имён через запятую; модель всегда явная. Проверить actual child model по JSON-событиям, `cwd`, завершение/ошибки и доступные tools. Для workflow достаточно последовательных независимых проверок; parallel/chain не обязательны для v1 и не должны быть условием PoC. Дочерний процесс не должен получать новые параметры, отсутствующие в выбранном расширении.

**Trust и окружение:** проектные агенты читаются расширением отдельно от trust-gated settings Pi. Отсутствие trust в child может пропустить настройки, а UI-confirmation S4 — отдельный вопрос. В v1 настройку доверия выполняет пользователь отдельно; blueprint не пишет `trust.json` и не добавляет `--approve`. Если политика пользователя запрещает сохранённое trust, а выбранный интерфейс не обеспечивает согласованный одноразовый режим child, запуск блокируется и решение пересматривается. Проверить глобальные расширения/MCP и коллизии инструмента `subagent`; произвольное наследуемое окружение и temp-файлы не sandbox. Отсутствие `--no-extensions`/`--no-mcp` нельзя компенсировать вымышленным frontmatter.

**PoC до интеграции:** одна минимальная тестовая роль, синтетический файл без секретов, явно выбранная доступная модель, один запрос чтения. Отдельно проверить неверный ID, пустой/некорректный tools, коллизию user/project, запуск из вложенного каталога, untrusted child, ошибку и отмену. Parent с `-e` не гарантирует те же child flags. Сначала offline-тесты обнаружения/аргументов; live только после согласования проекта, модели, стоимости, temp/cache следов и способа auth. Не переносить глобальную конфигурацию целиком в fixture.

**Лицензия/обновления:** S1 указывает MIT, но текст LICENSE в корне установленного пакета не найден. Для будущей поставки кода нужны подтверждённый upstream ref, полный текст лицензии и copyright notices для выбранной версии, проверка зависимостей/локальных патчей, журнал изменений и повторные compatibility tests. MIT-метаданные Pi не доказывают происхождение пользовательских модификаций S3. В v1 blueprint не распространяет этот код и не обновляет его автоматически.

**Влияние:** роль/генератор зависят от успешного PoC; installer только диагностирует совместимость, не устанавливает расширение. **Риски / пересмотр:** обновления Pi, неустойчивый JSON/extension API, неизвестные инструменты, невозможность trust или корректной отмены. Если без форка нельзя удовлетворить минимальный контракт, остановиться и отдельно согласовать узкий форк, не расширять scope в процессе. **Локально:** метаданные/diff/хеши уже проверены; runtime, abort и отсутствие лишних side effects ещё нет. **Пользователь:** утверждает кандидат, тестовое окружение и любое дальнейшее подключение/доставку зависимости.

### D3. Установка и обновления

**Статус:** `approved` (утверждено 2026-10-11, см. [p0-approvals.md](p0-approvals.md)).

**Проблема и ограничения.** Нужно сохранять пользовательские инструкции и неизвестные настройки, отличать собственные ресурсы от чужих и восстанавливаться после прерывания. Одного `cp` или Git rollback недостаточно: проект может быть dirty или без Git. Project-local declaration пакета не доказывает, что все cache/install записи остаются в проекте (S2).

| Вариант | Плюсы | Минусы и сопровождение |
|---|---|---|
| Копирование по плану с manifest | Полный diff и контроль назначения, offline из фиксированного snapshot, обычные проектные файлы | Собственный reconciliation/rollback. Средняя стоимость, рекомендуется v1 |
| Только Pi-пакет | Стандартная доставка extensions/skills/prompts/themes и pin | Нет стандартного ресурса agents или слияния `AGENTS.md`; package manager не решает model drift/backup. Низкая стоимость доставки, высокая доработка недостающего |
| Гибрид: пакет для расширения/ресурсов, генератор для проекта | Разделён lifecycle executable dependency и назначений | Две версии/два механизма обновления, больше состояний отказа. Средняя–высокая стоимость; отложить |

**Рекомендация v1:** проектное копирование из выбранной неизменяемой версии blueprint; subagent остаётся предусловием D2. Не сетевой bootstrap, не package installer. Предлагаемый минимальный runtime установщика — отдельная локальная CLI на Node.js >=22.19 (уже требуется Pi 1.1.0), вне model tools; выбор библиотек/упаковки проверяется отдельно. Чистые планирование и генерация отделены от файлового применения. Сейчас никакой CLI не создаётся.

Будущий `.pi/blueprint/install-manifest.json` с `schemaVersion: 1` хранит: blueprint revision, generator version, compatibility descriptor, source/config hashes, список управляемых project-relative путей, тип владения (`whole-file`, `marked-block`, `json-keys`, `frontmatter-fields`), последний применённый хеш/значение каждой управляемой части. Manifest не даёт права перезаписывать файл; отсутствие/повреждение manifest блокирует update до ручной сверки, не означает владение всем каталогом. Полные pre/post хеши нужны для транзакции; для drift учитываются управляемые части, чтобы не отвергать независимую пользовательскую правку тела агента.

Процедура применения дополняет [сценарий](../install/scenario.md):

1. **План без записи:** установить canonical root, проверить каждый компонент пути, symlink, hardlink и коллизии; v1 отклоняет link-пути для управляемых записей, включая backup/staging. Показать создаваемые каталоги, файлы, изменения управляемых частей, backup и удаления. Не создавать даже manifest до согласия.
2. **Reconciliation:** файл не принадлежит blueprint → конфликт; `current == last-applied` → допустимо предложить update; `current == desired` → no-op; иначе → пользовательское решение. Для runtime-полей моделей действует D1. Для чужих/изменённых тел ролей не делать автоматический three-way merge. Варианты: сохранить и явно отметить расхождение, пропустить зависимую настройку, либо утвердить конкретный объединённый diff. Пропуск не означает полностью успешную установку.
3. **Согласованный apply:** подтвердить plan digest и preimage hashes непосредственно перед записью. Один писатель, lock внутри проекта после согласия; при параллельном изменении — остановка. Staging, журнал транзакции и резервные копии в `.pi/blueprint/backups/<transaction-id>/`, без внешнего temp. Сохранять байты/режимы файлов; не записывать credentials. Backup может содержать приватные настройки: ограничить права, не добавлять в Git автоматически, отдельно согласовать ignore/срок хранения.
4. **Частичная ошибка:** журнал содержит перечень операций, pre/post hashes и статус каждой. Замена отдельного файла через rename, но **не обещается атомарность нескольких файлов**. Manifest фиксируется последним; незавершённая транзакция блокирует новые apply. После сбоя показать фактическое состояние. Восстановление — по заранее согласованному плану либо новому подтверждению, только если текущие байты совпали с записанными транзакцией; чужую последующую правку не затирать. Новые файлы удалять только при совпадении postimage. При crash остаются journal/backup для ручного или последующего безопасного восстановления.
5. **Повтор/обновление:** тот же source/config → no-op без дублирования блоков. Переход old revision → new revision сравнивает manifest, текущие файлы и новые ресурсы, явно показывает миграцию schema/пресетов. Неизвестная миграция блокируется; удалённый upstream-ресурс удаляется лишь отдельным согласованным пунктом и только если не изменён пользователем. Нет `git reset`, удаления всего `.pi` или очистки чужих файлов.

Settings патчить по двум модельным ключам, сохраняя неизвестные ключи и пользовательское форматирование где возможно; неподдерживаемый синтаксис — блокер, не переформатирование вслепую. Тела ролей обновлять отдельно от модельных полей. Все пути после разрешения должны оставаться внутри согласованного проекта; внешний OpenSpec store и любые глобальные записи требуют отдельного разрешения. Для v1 внешнее назначение лучше остановить как неподдерживаемое, а не расширять границы автоматически.

**Влияние:** до кода утвердить формат plan/manifest/journal, ownership и failure matrix. Минимальная v1 уже включает backup, повторную установку, update неизменённых ресурсов, конфликты и crash recovery; это не функции «на потом». **Отложить:** package delivery, автоматическое слияние пользовательских патчей, фоновые обновления, garbage collection backup, универсальные миграции старых schema и uninstall.

**Риски / пересмотр:** гонки с внешним процессом, права/диск, сетевые FS, чувствительные backup. V1 — проверенная локальная FS/платформа, не защита от злонамеренного конкурентного процесса; неподдерживаемые платформы обозначать явно. **Локально:** fixtures dirty/no-Git, повтор, drift, symlink escape, ошибка на каждой записи и восстановление. **Пользователь:** утверждает root, платформу v1, layout, ownership, backup/ignore-политику и каждый конкретный apply; архитектурное согласие не заменяет согласие на установку.

### D4. Доставка инструкций

**Статус:** `approved` (утверждено 2026-10-11, см. [p0-approvals.md](p0-approvals.md)).

**Проблема и ограничения.** Нужны загружаемая точка входа и разрешимые ссылки, но не замена пользовательского system prompt. Markdown-ссылка не является автоматическим include (S2/S5): модель нужно явно инструктировать прочитать документ, а в проверке убедиться, что это произошло.

| Вариант | Плюсы | Минусы и сопровождение |
|---|---|---|
| Управляемый блок корневого `AGENTS.md` + справочный снимок | Видимая точка входа, сохраняется основной контекст, без executable hook | Нужно разрешать приоритет `CLAUDE`/override и проверять чтение ссылок. Низкая–средняя стоимость |
| `.pi/APPEND_SYSTEM.md` или `SYSTEM.md` | Инструкции непосредственно в system prompt | Project trust; вытеснение одноимённых пользовательских файлов, SYSTEM заменяет стандартный prompt. Высокая цена конфликтов; не default |
| Skill/prompt по ручному вызову | Опциональное подключение без root merge | Не всегда вызывается, не подходит как единственная обязательная точка входа. Низкая стоимость, только дополнение |

**Рекомендация v1:** один маркированный блок `pi-pipeline-setup` в корневом `AGENTS.md`: краткие неизменяемые ограничения и явное требование сначала прочитать правила/Orchestrator/workflow. Остальной файл сохраняется. Границы блока учитываются manifest D3; повреждённые/дублирующиеся маркеры — конфликт. Никаких `orchestrator.md` в `.pi/agents/`.

Предлагаемый layout целевого проекта (пока не создаётся):

```text
AGENTS.md                         # управляемый блок, не полная замена
.pi/
  blueprint-models.yaml            # редактируемый источник назначений D1
  settings.json                    # только согласованные ключи defaults
  agents/<six-role-names>.md        # runtime definitions, без orchestrator
  blueprint/
    README.md                      # сведения о подключении, версии, ручные операции
    install-manifest.json          # ownership D3
    config/models.yaml             # неизменяемый снимок пресетов D1
    rules/AGENTS.md
    workflow/orchestrator.md
    docs/{workflow,roles,model-configuration,architecture}.md
    docs/implementation-plan.md
    agents/README.md
    install/{README,scenario}.md
    openspec/{README,conventions,templates/...}.md
    backups/<transaction-id>/      # локальные приватные recovery-данные
```

Список документов в дереве иллюстративный: точный install manifest включает **замыкание локальных ссылок** выбранных документов (в том числе справочный `openspec/config.example.yaml`, если на него ссылаются). Blueprint-документация сохраняет относительную иерархию, а root-блок ссылается на `.pi/blueprint/...`. Справочный `openspec/` внутри snapshot не рабочий planning root. Недостающий документ — ошибка сборки/установочного плана, не ссылка на Интернет вместо локальной инструкции. README snapshot явно отличает справочные source-пути от runtime-путей проекта.

**Конфликты до записи (S5):**

- Есть `AGENTS.md` → предложить только маркированное дополнение, проверить совместимость содержания.
- Есть только `CLAUDE.md`/`CLAUDE.MD` → новый `AGENTS.md` его вытеснит. По умолчанию блокировать. Пользователь отдельно выбирает сохранение действующей точки входа или создание `AGENTS.md` с явным поручением прочитать исходный `CLAUDE.md` и проверкой загрузки; автоматической миграции нет.
- Есть `AGENTS.override.md` или нестандартный регистр → определить реально выбранный файл; блок в невидимом `AGENTS.md` не считать подключением. Объединение с эффективным override требует отдельного согласия.
- Учитывать родительские/пользовательские и вложенные инструкции, а не только root. Конфликт требований — вопрос пользователю, не декларация абсолютного приоритета blueprint.
- `.pi/SYSTEM.md`, `.pi/APPEND_SYSTEM.md` и их пользовательские аналоги не создавать/менять по умолчанию. Файлы `SYSTEM.md`/`APPEND_SYSTEM.md` в иных местах исследовать как пользовательские, не обещать их автозагрузку.

Стековые профили не обязательны v1. Ядро описывает контракты и доказательства без Maven/Gradle/npm-команд. Будущий выбранный `stacks/<name>/` добавляет только технологии/команды и проверки совместимости, не собственные роли/gates и не автоматический запуск по обнаруженному стеку.

**Влияние:** renderer блока и validator ссылок/context precedence; smoke-test основной сессии из согласованного cwd. **Риски / пересмотр:** модель не читает ссылку, контекст слишком велик, новый loader Pi, вложенный запуск с другим `.pi`. При систематическом пропуске инструкций пересмотреть доставку после испытаний, не объявлять ссылки принудительным include. **Локально:** source loader/relative paths проверяются без запуска модели; фактическое чтение проверяет PoC. **Пользователь:** утверждает layout, root merge и каждую коллизию существующих инструкций.

### D5. Исполняемое QA

**Статус:** `approved` (утверждено 2026-10-11, см. [p0-approvals.md](p0-approvals.md)).

**Проблема и ограничения.** Независимость QA не означает самостоятельный shell. Тесты могут писать, обращаться к сети/базам/секретам; child Pi не изолирован (S2–S4). Нужна честная проверка поведения без неподтверждённого «QA passed».

| Вариант | Плюсы | Минусы и сопровождение |
|---|---|---|
| Статический анализ + существующие CI/пользовательские логи | Минимальные полномочия, нет runner в blueprint | Возможны устаревшие/неполные логи; QA не заявляет самостоятельное исполнение. Низкая стоимость |
| Пользователь вручную запускает проверенные команды | Контроль окружения и внешних последствий | Медленнее, нужна воспроизводимая привязка к редакции; ручной запуск сам по себе не sandbox. Средняя организационная стоимость |
| Отдельная sandbox/runner | Самостоятельное выполнение с проверяемыми ограничениями | Образы, mounts, сеть, secrets, cleanup, ресурсы и платформы. Высокая постоянная стоимость |

**Рекомендация v1:** первые два варианта совместно. QA получает `read, grep, find, ls`, проверенный набор расширений/MCP и одну редакцию с Reviewer; составляет матрицу критериев. При нехватке доказательств формирует запрос на конкретные команды/окружение, пользователь или уже существующий CI выполняет их отдельно. Blueprint не запускает CI, не создаёт runner и не снабжает QA произвольным bash.

Минимальный пакет доказательств: commit и/или snapshot digest D6, полный набор проверяемых изменений (включая untracked), команда/cwd, кто и где запускал, версии среды, время, exit code, логи stdout/stderr с отметкой редактирования/усечения. Без совпадения редакции результат помечается `not-verified`; повторные проверки после исправлений обязательны в затронутых областях. QA независимо оценивает полноту/результат логов Developer, но не называет это независимым запуском. Неизвестные/непройденные критерии показываются на Gate B как блокеры или явно принимаемые пользователем остаточные ограничения, а не скрываются.

Будущий runner требует отдельного решения: весь проверяющий процесс внутри границы ОС; read-only исходники или одноразовая копия, отдельные build/cache, запрет production secrets и docker socket, сетевой allowlist/отключение сети, лимиты и cleanup. Worktree/копия и запрет shell словами этим требованиям не равны.

**Влияние:** нужен формат отчёта и evidence checklist, не исполнитель тестов. Code Reviewer остаётся отдельной обязательной ролью и не получает отчёт QA как замену собственной проверке. **Риски / пересмотр:** происхождение логов, flaky tests, невозможность ручного воспроизведения. Runner обсуждать, когда реальные задачи требуют автоматического исполнения, а не ради названия QA. **Локально:** проверить матрицу на синтетических pass/fail/stale/missing/truncated логах, без запуска чужих тестов. **Пользователь:** принимает границу v1 и даёт отдельное разрешение на реальные команды/внешние ресурсы; финальная приёмка всё равно Gate B.

### D6. Хранение согласований

**Статус:** `approved` (утверждено 2026-10-11, см. [p0-approvals.md](p0-approvals.md)).

**Проблема и ограничения.** Согласие должно переживать смену сессии и относиться к конкретному содержимому, а не только имени change. Запись процесса не подпись и не технический запрет переходов. Текущий workflow уже допускает раздел в существующем proposal; предлагаем конкретизировать его, не создавать новый workflow state machine.

| Вариант | Плюсы | Минусы и сопровождение |
|---|---|---|
| Только сессия Pi | Сохраняет исходную реплику пользователя | Ветка/compaction/недоступность другой машине затрудняют поиск. Низкая запись, высокая стоимость восстановления |
| Сессия + раздел в `proposal.md` | Переносимость с change, соответствует текущему workflow, обычный Markdown | Требуются снимки и дисциплина; нет защиты от подделки. Низкая–средняя стоимость; рекомендуется для v1 |
| Отдельный `approvals.md` или state JSON | Нет служебного шума в proposal; JSON удобнее валидировать | Новый формат/миграции, риск двух источников текущего статуса. Средняя стоимость; отложить до нужды в автоматизации |

**Рекомендация v1:** исходная явная реплика остаётся в журнале сессии; Orchestrator дописывает в `proposal.md` отдельный маркированный раздел `Blueprint approvals`, не меняя требования Analyst. При первом подключении формат/маркеры и запись согласуются. Записи логически append-only: исправление новой записью со ссылкой `supersedes`, не стиранием старого решения. Это правило поведения, не immutable storage.

Каждая запись содержит: `record-id`, время с timezone, change ID и фактический root, `gate` (A/B), точную цитату решения пользователя и `decision` (`accept`, `reject`, `changes-requested`), ссылку session/branch/message если доступна, snapshot ID и перечисление файлов/хешей, принятый scope, открытые замечания с ID/важностью/решением/владельцем, ссылки на Reviewer/QA и тестовые доказательства для B. Неясная реплика — уточнение, не `accept`. Для переносимости цитата обязательна: локальная ссылка на сессию может быть недоступна другому участнику. При сомнении в подлинности/полноте — повторно спросить пользователя.

**Привязка редакции без самоссылки:**

- Для Gate A фиксировать SHA-256 байтов `proposal.md` **без единственного маркированного раздела журнала**, `design.md`, `tasks.md`, всех delta specs, metadata change (включая `skip_specs`) и влияющей конфигурации OpenSpec. Явно перечислять пути и отсутствующие опциональные файлы. Изменение границ маркеров или дубликаты — ошибка снимка. Вне журнала ничего не нормализовать молча.
- Snapshot ID вычислять по упорядоченному manifest: относительный путь, тип/режим, длина, хеш/признак удаления; формат сериализации/version зафиксировать в P5 (спецификация снимков и test fixtures), не в модельном P2. Snapshot-доказательства хранить в будущем `review-evidence/<snapshot-id>/` внутри change: manifest и необходимые копии/патч без секретов, не только невосстановимый digest. Каталог evidence и служебный раздел не включаются в собственный digest; ссылки на доказательства проверяются отдельно.
- Для Gate B добавить base commit/tree (если Git есть), точный diff index/worktree относительно согласованной базы, все новые/untracked и бинарные файлы результата, удаления, актуальные tasks, два отчёта и логи. Один `git diff` или один commit недостаточен для dirty tree. Без Git согласовать базовый файловый снимок. Внешние логи хранить с digest и доступной ссылкой либо копией; недоступные доказательства отмечать как непроверенные.
- Пользователь видит содержимое и ID снимка **до** реплики согласия; после записи журнала повторно сверяются fingerprints. Mismatch делает согласие устаревшим, не исправляется переписыванием старого ID.

Изменение scope/требований/дизайна/плана требует повторного Gate A по текущему workflow. Переключение чек-боксов задач при неизменном плане — прогресс: фиксируется новый снимок и связь с Gate A, не автоматическое разрешение новых задач. Любой иной mismatch сначала объясняется пользователю; нельзя автоматически объявить его косметическим. После Gate B изменение принятой реализации/результатов требует затронутых повторных проверок и Gate B. Дописывание самого журнала и ожидаемая операция архивирования не новые продуктовые изменения.

**Архивирование:** запись `archive-attempt` с Gate B record/snapshot перед командой, после — `archive-result` с exit status, фактическим архивным путём, проверкой переноса и ожидаемой синхронизации базовых specs. Успех фиксируется только после проверки; при переносе result дописывается в раздел proposal уже в архиве. Ошибка/частичная синхронизация остаётся незавершённой с описанием recovery. Если после crash result отсутствует, сначала сверить active/archive и baseline, а не повторять команду вслепую. Сохранность служебного раздела/evidence при archive нужно проверить на OpenSpec 1.14.0 (S6); иной root/store требует отдельного разрешения.

**Влияние:** нужны документированный формат журнала, snapshot checklist и впоследствии небольшой helper для fingerprints; ни автоматического извлечения согласия моделью, ни gate enforcement v1. При возобновлении Orchestrator проверяет запись, снимок и открытые замечания; отсутствие подтверждения — остановка. **Риски / пересмотр:** ручная подделка/ошибка, секреты в evidence, рост архива, сложные Git submodules/LFS. Такие случаи требуют отдельного решения о составе snapshot; криптографические подписи/центральный audit log — только при реальной потребности. **Локально:** fixtures изменения байтов, untracked/binary, утраты сессии, supersedes и ошибки archive. **Пользователь:** утверждает формат, хранение evidence/приватность и каждый Gate; Markdown не блокирует инструменты, CLI или ручной переход.
