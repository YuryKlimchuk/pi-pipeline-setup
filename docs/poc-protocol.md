# Протокол PoC одного subagent (P1 → P3)

> **Редакция:** 1. Дата: 2026-10-11.
> **Статус:** протокол подготовлен, **PoC не запускался**. Live-проверки запрещены до отдельного разрешения пользователя.

Цель протокола — подтвердить минимальный контракт subagent-кандидата **S4** (пример из Pi 1.1.0) одним вызовом в disposable-проекте без пользовательских данных и секретов. Проверяется именно кандидат S4; свойства S3 и иных реализаций на него не переносятся.

## 0. Границы

- Никаких live-запросов к моделям, установки/подключения расширения, изменения trust/permissions/глобальной конфигурации Pi до отдельного разрешения пользователя.
- Проект disposable: одноразовый каталог вне рабочих проектов, без пользовательских данных, секретов и credential-файлов.
- Кандидат подключается к disposable-окружению пользователем (или согласованным способом), не автоматически и не в рабочую сессию.

## 1. Проверяемые гипотезы

- H1 **Discovery:** при `agentScope: project` кандидат находит ожидаемый `.pi/agents/*.md` в disposable-проекте (из корня и из вложенного каталога).
- H2 **Модель:** явно заданная модель передаётся child и подтверждается фактическим событием дочернего процесса, а не только полем `details.model`.
- H3 **Инструменты:** согласованный набор `tools` реально действует в child; наличие имени в списке не принимается за доказательство доступности.
- H4 **Инструкции/контекст:** тело роли и задача фактически прочитаны child (не только переданы аргументами).
- H5 **Процесс:** child работает в ожидаемом `cwd`, завершается с ожидаемым exit code, ошибки не маскируются.
- H6 **Побочные эффекты:** перечислены все записи вне проекта (temp/cache/session) и они соответствуют ожиданиям.

## 2. Минимальные предпосылки

- Установлены и зафиксированы версии: Pi 1.1.0, OpenSpec CLI 1.14.0, Node v22.22.3 (подтверждено в [compatibility.md](compatibility.md)).
- Кандидат S4 зафиксирован по SHA-256: `index.ts` `4facaa61c9c781748dd000eb5d2ec0a75289986d1a6e11ce13971ca5653dc252`, `agents.ts` `cc85ecd33b89aa575bea3d2a9a9da7654a6305da4de02e5041aa5342a1de29b4`.
- Одна минимальная тестовая роль (не полноценное определение роли v1) с `name`, `description`, явным `model`, непустым `tools` (read-only подмножество, например `read, ls`).
- Один синтетический файл для чтения (без секретов), например `fixture.txt` с известным содержимым.
- Явно выбранная доступная модель и способ auth, согласованные отдельно; лимит расходов/данных.
- Disposable-проект инициализирован как отдельная копия, не рабочий репозиторий.

## 3. Последовательность действий

1. Зафиксировать baseline disposable-проекта: список файлов, хеши, `git status` (если есть Git), отсутствие секретов.
2. Подключить кандидата S4 в disposable-окружение (вне рабочей сессии), исключив дублирование инструмента `subagent`.
3. Offline-проверки (без модельных запросов) — см. раздел «Offline-проверки».
4. Получить отдельное разрешение пользователя на live-read.
5. Выполнить **один** single-вызов: `{ agent, task, agentScope: "project" }`, задача — прочитать `fixture.txt` и вернуть его содержимое/подтверждение.
6. Собрать JSON-события дочернего процесса и exit code.
7. Сверить фактическую модель и набор инструментов по событиям (раздел 6).
8. Зафиксировать побочные эффекты и состояние после (раздел 8).
9. Выполнить очистку тестовых артефактов (раздел 9).

## 4. Ожидаемые результаты

- Найден один проектный агент; `projectAgentsDir` указывает на `.pi/agents` disposable-проекта.
- Child запущен с `--mode json -p --no-session`, явным `--model`, `--tools`, `--append-system-prompt <temp>` и задачей.
- В JSON-событиях child присутствует assistant-сообщение с ответом, ссылающимся на содержимое `fixture.txt`.
- Exit code `0`, `stopReason` = `end` (или эквивалент успешного завершения).
- Фактическая модель в событиях child совпадает с заданной.
- Все побочные записи перечислены; временный prompt-файл удалён.

## 5. Критерии pass / fail / inconclusive

- **pass:** H1–H6 подтверждены наблюдаемыми событиями; фактическая модель и набор инструментов совпали с ожиданием; ошибок/скрытых сбоев нет.
- **fail:** любая из гипотез опровергнута (агент не найден; модель/инструменты не совпали; child не прочитал задачу; ненулевой exit при корректном вводе; неожиданная запись вне проекта). Возврат к D2, не расширять scope.
- **inconclusive:** недостаточно наблюдаемых данных для решения (например, события не позволяют однозначно установить модель/инструменты или окружение воспроизведено не полностью). Зафиксировать пробел и запросить уточнение, не объявлять pass.

## 6. Проверка фактической модели и набора инструментов

- Модель: анализировать JSON-события дочернего процесса (`message_end`/аналоги) на предмет фактически использованного `model`; поле `details.model` результата само по себе не доказательство (изначально содержит запрошенную модель).
- Инструменты: подтвердить, что child реально объявил/использовал ожидаемые имена tools; `--tools` — это декларация для модели, не граница ОС и не sandbox. Отдельно зафиксировать доступные расширения/MCP, которые могут расширять фактический набор.

## 7. Ошибки запуска, отмена и завершение

- Отдельно проверить (по отдельному разрешению): неверный model ID; пустой/некорректный `tools`; коллизию user/project имён; запуск из вложенного каталога; untrusted child; ошибку модели; отмену (SIGTERM → SIGKILL) и завершение процесса.
- Каждый сценарий фиксирует exit code, stderr, stopReason и фактическое состояние после завершения; ошибки не маскируются.

## 8. Файловые побочные эффекты

- Зафиксировать до/после: временный prompt-файл (создан/удалён), любые session/cache/log-следы child вне disposable-проекта, изменения внутри проекта.
- Сравнить список файлов и хеши до и после; не ограничиваться exit code.

## 9. Очистка тестовых артефактов

- Удалить disposable-проект и любые созданные fixture-файлы после снятия показаний.
- Убедиться, что в рабочем проекте и в `~/.pi/agent/` не осталось изменений (сравнить с baseline).
- Не удалять автоматически ничего вне согласованного disposable-scope.

## 10. Условия остановки и необходимые разрешения

- Остановиться, если: кандидат отличается по SHA-256/версии; требуется изменение trust или глобальной конфигурации; нет согласованного способа auth/модели; обнаруживается запись вне согласованного scope; политика пользователя запрещает сохранённое trust, а headless-режим не обеспечивает одноразовое подтверждение.
- Необходимые отдельные разрешения: live-запрос (модель и стоимость), способ auth, подключение кандидата в disposable-окружение, запись fixture, внешние temp/cache-следы.

## Offline-проверки (разрешены без модельных запросов)

- Сверка SHA-256 кандидата S4.
- Discovery из корня и вложенного cwd (без запуска модели — построение списка агентов).
- Коллизия user/project имён при `both`.
- Неверный/пустой `tools`, неверный frontmatter.
- Построение аргументов child (статически или dry-run без запроса).

## Live-проверки (запрещены до отдельного разрешения пользователя)

- Единственный single-вызов с чтением синтетического файла (после разрешения модели/стоимости/auth).
- Отрицательные сценарии: ошибка модели, отмена, завершение.
- Проверка фактической модели/инструментов по событиям.

Live-проверки не выполняются в рамках P1 и не начинаются автоматически после него.
