## Границы и порядок

Сохраняются [workflow 1–10](workflow.md), [семь ролей](roles.md), независимые Reviewer/QA и оба Human Gate. Нумерация ниже — пакеты будущей работы, **не новая нумерация workflow**. Для каждого реализационного изменения нужны согласованные артефакты и Gate A; завершение включает независимые проверки, Gate B и архивирование. Наличие этого плана не заменяет их.

Нельзя автоматически устанавливать зависимости, менять пользовательские настройки Pi, записывать trust, инициализировать OpenSpec или создавать change вне явного согласованного корня. При отсутствии рабочего OpenSpec пользователь отдельно решает вопрос инициализации; справочный `openspec/` этого репозитория не считать готовым change root.

Зависимости: **P0 → P1 → P2 → P3 → P4 → P5 → P6a → P6b → P7 → P8**. Schema согласуется до PoC, но её исполняемый генератор — только после подтверждения контракта subagent. Проектирование безопасности установщика отделено от его реализации. Тесты добавляются с каждым этапом; P7 — дополнительная интеграционная проверка, не первый момент тестирования. Сроки и трудозатраты пока не определяются.

- **Результат:** [docs/p0-approvals.md](p0-approvals.md) — дата, область утверждения и точный перечень D1–D6; платформа v1 (Linux + локальная FS), кандидат расширения (пример S4 из Pi 1.1.0), QA-mode (статика + внешние логи) и privacy policy evidence/backups.
- **Завершение:** критерий выполнен — D1–D6 утверждены; нерешённых вопросов, меняющих scope первой версии, нет; отложенное отделено от блокеров (см. `blocked`/`not-tested` в [compatibility.md](compatibility.md)).
- **Проверки:** согласованность с workflow/ролями; отсутствуют обещания sandbox или автоматической инициализации.
- **Зависимости:** нет.
- **Согласование:** обязательно. Частичное утверждение позволяет только не зависящие от открытого решения работы; не даёт общего разрешения на реализацию.

## P1. Технические предпосылки и compatibility matrix

**Статус:** завершён (2026-10-11). PoC (P3) не выполнялся.

- **Цель:** подтвердить воспроизводимый контракт целевого окружения до поставки ресурсов.
- **Вход:** P0, согласованное окружение/корень исследования; Pi/OpenSpec/Node версии, S1–S6, выбранный subagent source/ref.
- **Результат:** [docs/compatibility.md](compatibility.md) — versions, platform, hashes, upstream reference, лицензия/notice status, discovery/trust/tools/model/child invocation matrix, список `verified / not-tested / blocked`; [docs/poc-protocol.md](poc-protocol.md) — протокол PoC (не выполнялся).
- **Завершение:** критерий выполнен — известны источник и точные байты кандидата; отделены локальная S3 и пример S4; определены команды и наблюдения PoC, все внешние записи и расходы перечислены.
- **Проверки:** статический diff расширений, metadata и license notices; контекст AGENTS/CLAUDE/override, model CLI, project trust в headless child, фактический planning root OpenSpec; никаких init/new change для диагностики. Auth/model requests не выполнялись.
- **Зависимости:** P0.
- **Согласование:** перед расширением области чтения/запуском непроверенного кода; завершение с go/no-go пользователя на PoC. При несовместимости — возврат D2, а не незаметный форк.

## P2. Формат моделей и контракты выходных данных

**Статус:** не начат.

- **Цель:** зафиксировать D1 как проверяемый формат, без преждевременного применения к рабочему проекту.
- **Вход:** утверждённый D1, P1, каноническая таблица профилей.
- **Результат:** после отдельного разрешения — спецификация формата, schema/валидирующие fixtures (предлагаемый `schemas/model-configuration.schema.json`, `tests/fixtures/models/`), точное описание сериализации/pin и managed fields. Fixtures содержат синтетические примеры, не рабочую конфигурацию. Согласно D1, `config/models.yaml` и проектный `.pi/blueprint-models.yaml` до генератора не создаются; их создание проверяется в P4.
- **Завершение:** три полных профиля и семь назначений разрешаются однозначно; ModelRef сохраняет точные provider/id; определены ошибка неизвестной schema, duplicate keys, отсутствующих уровней и конфликтов назначения.
- **Проверки:** все профили, одна модель на несколько уровней, шесть subagent overrides и отдельный Orchestrator, provider/id со слешем/двоеточием, неизвестная роль, одновременные level/model, drift source/runtime. Никаких вымышленных реальных ID в presets; fixture IDs помечены как синтетические.
- **Зависимости:** P1; утверждение D1. Язык/библиотека validation выбираются явно; зависимости пока не устанавливать без отдельного разрешения.
- **Согласование:** формат/fixtures до генератора; любые изменения согласованных приоритетов возвращаются пользователю.

## P3. Минимальный PoC одного subagent

**Статус:** не начат; PoC не выполнялся.

- **Цель:** подтвердить запуск и фактическую модель, а не только синтаксис frontmatter.
- **Вход:** P1–P2, одобренный кандидат расширения, disposable проект без секретов, доступный точный ModelRef, способ auth/trust и лимит расходов/данных.
- **Результат:** минимальная тестовая роль, не производственный каталог; предлагаемые `tests/fixtures/subagent-poc/` и `docs/compatibility.md` с санитизированными результатами. Один синтетический файл для чтения; никаких изменений глобального Pi. Подключение кандидата должно исключать дублирование инструмента `subagent`.
- **Завершение:** `agentScope: project` находит ожидаемый путь; child работает в ожидаемом cwd; заданная модель подтверждена JSON-событием, а не только echo `details.model`; согласованный набор tools реально действует; ошибки не маскируются. Глобальная конфигурация не изменилась, все runtime temp/cache следы известны.
- **Проверки, сначала offline:** discovery из root/вложенного cwd, user/project collision, неверные frontmatter/tools/ID, построение аргументов. Затем отдельно разрешённый live-read; untrusted/trusted child, ошибка модели, отмена и завершение процесса. Проверить доступные расширения/MCP — список `--tools` не sandbox. Parent flags не считать автоматически наследуемыми child.
- **Зависимости:** P2; разрешённые окружение и модель. Доставка/подключение внешнего кода — отдельное действие пользователя, не автоматическая часть PoC.
- **Согласование:** до любых live-запросов, записи fixture, auth/trust операций или внешнего temp; после результатов — явный go/no-go на интеграцию D2. При провале остановиться, не создавать остальные роли на неподтверждённом контракте.

## P4. Шесть определений ролей и модельный resolver

**Статус:** не начат.

- **Цель:** реализовать контракты без привязки текста роли к провайдеру и без неявного наследования модели.
- **Вход:** успешный P3, утверждённые schema и tool contract, `docs/roles.md`.
- **Результат:** будущие `agents/{analyst,architect,developer,code-reviewer,qa,devops}.md` как исходные шаблоны; чистый resolver и генератор патчей (предлагаемый `src/models/`), unit tests. Вместе с генератором, после отдельного разрешения, создаётся `config/models.yaml` по формату P2; `.pi/blueprint-models.yaml` проверяется в тестовом fixture, не записывается в пользовательский проект автоматически. Шаблоны с незаполненной моделью не устанавливаются/запускаются: runtime-definition получается только после разрешения конкретного ModelRef.
- **Завершение:** все шесть runtime-ролей получают явный `model:`; Orchestrator представлен только defaults основной сессии. Полномочия и артефакты соответствуют каталогу, Reviewer/QA не исправляют реализацию и не получают shell. DevOps не заменяет независимую проверку.
- **Проверки:** frontmatter parser выбранной версии, lint контрактов, таблица разрешения профилей/overrides, сохранность тела и неизвестных settings, детерминированные патчи, недоступная модель и ручной drift. Resolver не пишет в FS и не делает API-вызовов.
- **Зависимости:** P3; D1/D2.
- **Согласование:** Gate A реализационного change; подключение к живому проекту не входит в этап. Перед продолжением показать определения и результаты проверок.

## P5. Orchestrator, доставка правил и протокол согласований

**Статус:** не начат.

- **Цель:** подключать основной workflow через инструкции, не изображая state machine.
- **Вход:** P4, D4–D6, существующие `workflow/orchestrator.md`, `rules/`, контекстные конфликты P1.
- **Результат:** шаблон маркированного root-блока, manifest справочного snapshot/проверка замыкания ссылок, шаблоны QA evidence и раздела `Blueprint approvals`; спецификация snapshot manifest/сериализации и тестовые примеры Gate A/B, `supersedes`, archive-result. Пути вспомогательных ресурсов согласовать до добавления, например `resources/` и `tests/fixtures/instructions/`.
- **Завершение:** один источник этапов сохранён; делегирование не пересекает gates; оба независимых отчёта обязательны; все статусы связаны с конкретной редакцией. Чтение linked docs требуется явно, не выдаётся за include. Нет автоматических hooks/переходов.
- **Проверки:** AGENTS/CLAUDE/override precedence, существующий SYSTEM/APPEND_SYSTEM, вложенный cwd, relative links в установленном layout; пропуск согласия, stale snapshot, open blocker, утрата session, изменённые checkbox/план, binary/untracked evidence и исключение журнала из собственного digest. QA отличает запуск от анализа логов.
- **Зависимости:** P4; D4–D6.
- **Согласование:** пользователь утверждает образец root merge, snapshot/journal/privacy contract. Live-проверка чтения инструкций требует отдельного разрешения на запрос. Не изменять рабочий AGENTS.md для проверки без согласия.

## P6a. Дизайн безопасного установщика

**Статус:** не начат.

- **Цель:** согласовать алгоритм до файловых мутаций.
- **Вход:** P4–P5, D3, выбранная платформа/FS v1.
- **Результат:** точечное уточнение `install/scenario.md`, спецификации plan/manifest/transaction journal и failure matrix; список файлов будущей CLI и тестов. Указать поддерживаемый JSON-синтаксис, способ сохранения форматирования, markers и границы ownership.
- **Завершение:** каждая операция имеет precondition, ожидаемый postimage и обратное действие; план перечисляет также directories/staging/backup/lock. Никакой записи до подтверждения. Известны правила совместимости schema и блокировки неподдерживаемой миграции.
- **Проверки:** table-top прогон first install/no-op/update/drift/skip/delete/partial failure; symlink и hardlink, чужой AGENTS, неизвестные settings, повреждённый manifest, stale plan, внешний OpenSpec store, no-Git и dirty tree.
- **Зависимости:** P5; D3.
- **Согласование:** обязательный review дизайна перед P6b; runtime CLI и библиотеки утверждаются до установки зависимостей. Инициализация OpenSpec не входит в installer.

## P6b. Реализация минимального установщика

**Статус:** не начат.

- **Цель:** применить только явно подтверждённый план в одном проекте.
- **Вход:** одобренный P6a, согласованные артефакты/Gate A, разрешение на необходимые зависимости (если нужны).
- **Результат:** будущие `src/install/`, CLI entrypoint, tests и руководство. Предлагаемые операции: plan, apply подтверждённого plan digest, inspect drift, recover; это проектируемый интерфейс, не существующие команды.
- **Завершение:** plan без записи; apply повторно проверяет hashes/root, пишет staging/backup/journal внутри root, фиксирует manifest последним. Неизвестные ключи/чужие файлы сохранены, ошибка не объявляется успехом. Реализованы no-op, update неизменённых ресурсов, ручные конфликты и recovery.
- **Проверки:** unit/integration тесты чистого resolver и FS writer отдельно; inject failure при каждой записи; несовпадение plan, disk/permission failure, дубли marker, невалидные settings и source schema. Ни глобальных install/update, ни trust/init/new change subprocess в установщике.
- **Зависимости:** P6a.
- **Согласование:** code change по обычному workflow; каждый реальный target apply требует отдельного preview/подтверждения. Noninteractive отсутствие подтверждения — остановка, не implicit yes.

## P7. Установка, обновления, конфликты и восстановление

**Статус:** не начат.

- **Цель:** доказать свойства D3 на fixtures до первого пользовательского внедрения.
- **Вход:** P6b, минимум два фиксированных blueprint snapshot, чистый и изменённый целевые fixtures.
- **Результат:** интеграционная матрица в будущем `tests/install/` и отчёт совместимости/остаточных ограничений; восстановительные инструкции по фактически поддержанным сценариям.
- **Завершение:** повторный apply даёт no-op; old→new не теряет пользовательские изменения; изменённая модель требует решения D1; частичный сбой восстанавливается или явно блокируется без уничтожения последующих правок. Отсутствуют неразрешённые записи вне fixture root.
- **Проверки:** first install, repeated install, stale manifest/plan, schema migration отказ, конфликт каждого типа ownership, пропуск зависимой настройки, удаление изменённого upstream-файла, crash между каждым шагом и commit manifest, восстановление после crash, symlink escape, lock contention, backup privacy и сохранность unknown keys. Сравнить содержимое и режимы файлов до/после; не ограничиваться exit code.
- **Зависимости:** P6b; fixture updates не выполняют реальные package updates.
- **Согласование:** результаты независимых Reviewer/QA и устранение блокеров перед разрешением на P8. Неподдержанные платформы явно исключаются из заявления готовности.

## P8. Полный workflow на тестовом проекте

**Статус:** не начат.

- **Цель:** проверить процесс человеком, а не доказать техническую блокировку gates.
- **Вход:** P7, отдельный согласованный тестовый проект, модели/бюджет, проверенное расширение, разрешённое test environment. Рабочий OpenSpec root уже создан пользователем либо его инициализация отдельно явно разрешена.
- **Результат:** один небольшой реальный тестовый change, полный набор артефактов, два независимых отчёта, логи, записи Gate A/B и archive-result; итоговый отчёт ограничений v1.
- **Завершение:** прослеживаются все этапы 1–10; явные решения пользователя относятся к предъявленным snapshots; минимум один сценарий исправления/повторной проверки; архивирование и синхронизация specs проверены, evidence сохранено. Основная сессия и шесть назначений моделей проверены отдельно, DevOps вызывается только при нужде.
- **Проверки:** отсутствие Gate A останавливает разработку; отсутствие Gate B останавливает архивирование инструкциями Orchestrator; изменение решения вызывает повторный A, изменение результата — проверки и B. Проверить stale logs, отказ модели, отсутствие безопасного QA и неуспешное archive с восстановлением. Негативные сценарии — в fixture, без намеренного повреждения рабочего проекта. Не заявлять, что прямой CLI-вызов запрещён Markdown.
- **Зависимости:** P7 и отдельное разрешение на тестовый проект, API-вызовы, стоимость и команды. Для проверки archive сначала использовать безопасную копию с согласованной областью записи.
- **Согласование:** настоящий пользователь проходит оба gates; финальный go/no-go на выпуск v1 после итогового review. Автоматическая приёмка или архивирование «ради теста» недопустимы.

## Не входит в первую версию

Workflow engine и технические gate locks; собственный fork subagent без отдельного решения; автоматическая установка расширений/зависимостей; управляемый sandbox/QA runner; live-YAML watcher; выбор модели по сложности без подтверждения; автоматическое слияние пользовательских патчей; глобальная настройка Pi; автоматический OpenSpec bootstrap; обязательные stack-specific профили.

## Следующее минимальное действие

P0 и P1 завершены (см. таблицу статусов выше). Следующий этап по порядку — **P2** (спецификация формата моделей и синтетические fixtures), он начинается только после отдельного согласования. Успешный P1 сам по себе не разрешает PoC (P3), live-запросы, подключение расширения, auth/trust или реализацию — они требуют отдельных разрешений.
