# Будущие определения subagents

> Здесь пока только документация. Полные определения агентов не реализованы.

Контракты задаёт **[docs/roles.md](../docs/roles.md)**. Планируемые файлы в этом каталоге и затем в `.pi/agents/` целевого проекта: `analyst.md`, `architect.md`, `developer.md`, `code-reviewer.md`, `qa.md`, `devops.md`. Orchestrator — основная сессия Pi, не файл subagent.

## Формат и обнаружение

В проверенном локальном расширении Markdown содержит обязательные `name`, `description`, необязательные `tools` (через запятую), `model` и тело инструкций, добавляемое через `--append-system-prompt`. Это контракт расширения, а не встроенный каталог ролей Pi.

- `agentScope: "project"` выбирает проектные роли; default `user` их не загружает. `both` допускается осознанно: проектные имена перекрывают пользовательские.
- Расширение ищет ближайший каталог `.pi/agents/` вверх вплоть до корня файловой системы, **не обязательно до корня Git**. Нужно проверить фактический путь и происхождение определений.
- `model:` предлагается генерировать явно для каждой роли из [единого источника назначений](../docs/model-configuration.md). Тело не зависит от модели/провайдера. Отсутствие поля не гарантирует наследование активной модели Orchestrator.
- Непустой `tools:` передаётся как `--tools`. Пустое/отсутствующее поле **не запрещает все инструменты**: расширение просто не передаёт ограничение.
- Результат роли должен быть самодостаточным для следующего запуска; отдельный процесс изолирует контекст, но не рабочие файлы.

## Reviewer и QA: три разных слоя ограничений

| Слой | Что предусмотрено | Что это гарантирует |
|---|---|---|
| Поведение | Не исправлять код/тесты; вернуть отчёт Orchestrator; не запускать мутирующие команды | Только инструкцию модели, не запрет ОС |
| Выбор инструментов | По умолчанию `tools: read, grep, find, ls`; без `bash`, `powershell`, `write`, `edit` | Ограничение выбранных инструментов через `--tools`, не sandbox и не ограничение путей |
| Техническая изоляция | Проверенный набор расширений/инструментов и отдельно настроенная среда с ограничениями ОС, если требуется сильная защита | Защита зависит от реальной конфигурации окружения; blueprint её пока не создаёт |

**«Чтение + bash без мутирующих команд» не является техническим режимом read-only.** Оболочка может писать, запускать скрипты, работать с сетью и секретами. Во frontmatter нет безопасного allowlist команд или read-only bash. Запрет словами, проверка по regex и project trust не создают такую гарантию.

Дополнительные ограничения Pi 1.1.0:

- `--tools` не является универсальной границей исполнения: MCP-инструменты имеют отдельные правила exposure; загруженные расширения исполняют код с правами процесса.
- CLI Pi предоставляет `--no-extensions`, `--no-mcp` и `--exclude-tools`, но **локальный subagent-инструмент не предоставляет полей для этих флагов** и сам их не добавляет. Не следует придумывать соответствующие поля frontmatter.
- `confirmProjectAgents` подтверждает запуск проектной инструкции (в локальной реализации только при доступном UI), не каждую shell-команду и не Gate A/B. Доверие проекту в дочернем JSON-процессе также проверяется отдельно от подтверждения определения роли.

## Наиболее безопасный практический вариант

По умолчанию Reviewer и QA выполняют статическое чтение с четырьмя указанными инструментами, после проверки реально загруженных расширений/MCP и происхождения инструментов. Нельзя объявлять даже этот вариант гарантированно read-only для файловой системы без внешнего ограничения прав; `read` также не ограничен корнем проекта.

Для QA, которому нужны исполняемые проверки:

- предпочтительно пользователь запускает проверенные команды в своей изолированной тестовой среде/CI и передаёт логи; QA отмечает, что анализировал логи, а не запускал тесты сам;
- либо весь процесс проверки запускается в отдельно подготовленной sandbox/контейнере: исходники read-only или одноразовая копия, отдельное место для сборки, без рабочих секретов, production-доступа и лишней сети;
- обычный worktree/копия без ограничений ОС не является sandbox. Общие базы, порты и build-каталоги исключают безопасный параллельный запуск;
- если безопасной среды нет — не выдавать произвольный bash ради формального «QA passed», а сообщить непроверенные сценарии и запросить ручные действия.

Контейнер, отдельный runner или усиление расширения — возможная будущая работа, **не поставляемый функционал**. Источники и различия реализаций: [архитектура](../docs/architecture.md).
